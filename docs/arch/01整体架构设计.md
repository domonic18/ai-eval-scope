## 一、设计目标与约束

### 1.1 设计目标

| 目标 | 说明 |
|------|------|
| **Agent 驱动执行** | 执行引擎由 DeepAgents（Python，开源）端到端驱动，Agent 理解任务、智能调用 SUT、采集结果 |
| **执行-评估解耦** | 执行引擎与评估引擎独立运行、独立演进，通过标准化数据包交互 |
| **评估确定性** | 评估统一由 PipelineEngine 执行，固定级联、结果可复现，LLM-as-judge 内建于 Evaluator |
| **通用可扩展** | 以课件生成为切入点，架构上支持代码生成、RAG、对话等多类 Agent 评估 |
| **模型无关** | LLM-as-judge 通过 Provider 抽象层接入，支持多厂商多协议；执行 Agent 使用 deepagents框架 |
| **离线优先** | 前期批量离线评估为主，接口预留流式扩展空间 |
| **可视化可追溯** | 提供 Web Portal 展示评估趋势与详细报告，支持按项目维度回溯 |

### 1.2 架构约束

- **技术栈**：Python 3.11+
- **Agent 框架**：`deepagents`（Python，LangChain 官方开源，双协议模型无关），执行引擎 ExecutionAgent 基于其端到端驱动
- **部署形态**：前期 CLI + Web Portal + REST API → 中期 Web 后端统一提供 REST API（`/api/v1/jobs` 等）+ executor 异步执行 → 远期 SaaS
- **Web 框架**：React + Express（TypeScript），腾讯云容器化部署
- **SUT 接入**：SUT 能力通过 MCP Tools 暴露给执行 Agent（HTTP 调用、CLI 调用、文件操作）
- **评估目标**：以 Markdown/HTML 文档集为主要评估对象（支持目录结构输入），暂不支持 PPTX
- **数据存储**：评估侧用 workspace 文件系统（可审计、易复用）；Web 可观测平台用 PostgreSQL（结构化）+ 对象存储（大制品）
- **认证授权**：Web 平台具备账号 + 组织/项目 + API Key 多租户隔离（见 09）；CLI 评估侧暂不涉及

三种运行模式：

| 模式 | 说明 |
|------|------|
| **pipeline** | ExecutionAgent 执行 → 评估引擎评估 → 报告 |
| **run-only** | 仅 ExecutionAgent 执行，生成 ExecutionPackage |
| **eval-only** | 从 workspace 加载 ExecutionPackage → 评估引擎评估 → 报告 |

### 2.4 核心机制

本系统采用**执行 Agent 化 + 评估 Pipeline 化**架构：

| 机制 | 说明 |
|------|------|
| **执行 Agent 化** | ExecutionAgent (DeepAgents) 端到端驱动执行：理解任务 → 构建请求 → 调用 SUT → 采集结果 |
| **SUT 即 MCP Tools** | SUT 交互能力（HTTP 调用、CLI 调用、文件操作）通过 MCP Tools 暴露给执行 Agent |
| **评估 Pipeline 化** | PipelineEngine + PipelineStage 执行固定级联流程，确定性高、无额外 token 消耗 |
| **评分确定性** | 评分聚合始终由 ScoreAggregator（确定性代码）执行 |
| **预算控制** | `max_turns` + `max_budget_usd` 双重控制，防止执行 Agent 成本失控 |

**设计原则**：执行智能化（Agent 理解任务、自适应执行），评估确定性（PipelineEngine 固定级联）。

### 2.5 配置管理子系统（Scenario Package）

> 系统已演进为**面向多场景**的评估框架，配置资产以 **Scenario Package（场景包）** 为第一公民组织，详见 [13 配置管理设计](./13配置管理设计.md)。本节给出与总体架构的衔接。

**核心概念**：

| 概念 | 说明 |
|------|------|
| **Scenario** | 评估场景命名空间（courseware / travel-itinerary / conversation-safety / code-generation / RAG / math benchmark 等） |
| **ScenarioPackage** | 一个场景的配置包，含规则集、提示词、数据集、SUTConfig、Inferencer、聚合策略、指标定义；本地包 + 线上包双向流通 |
| **Dataset** | 统一数据抽象，`role: test`（生成 TaskSet，如 GSM8K）或 `role: reference`（被评估器查询，如课件知识点）；通过 `DatasetBackend`（YAML/JSONL/HuggingFace/向量/API）加载 |
| **MetricDefinition / AggregationPolicy** | 场景化指标与聚合策略，替代硬编码的 DR/CPR/Reward |
| **RunConfigSnapshot** | 每次运行保存的不可变完整配置快照，保证可复现 |

**与三大子系统的关系**：

- **评估引擎**（04）：`ScenarioScoreAggregator` / `ScenarioMetricsCalculator` 按场景策略聚合与计算指标。
- **执行引擎**（03）：业务场景走 ExecutionAgent；benchmark（`role: test`）走 Inferencer + SUTConfig。
- **Web 平台**（09）：`Run.metrics` / `Sample.metrics` JSONB 统一存储场景化指标；前端按 `RunConfigSnapshot.metricDefinitions` 动态渲染；支持 Rule/Prompt/Dataset 的 Web 编辑与版本管理。

**资产演进**：原扁平 `evaluator/agent_eval/assets/{rules,knowledge,prompts}/` 一次性迁移为 `assets/packages/<scenario>/<package>/<version>/`，其中 `knowledge/` 作为 `role: reference` 的 Dataset 归入 `datasets/`。不保留旧路径兼容。

## 六、关键设计决策

| 决策点 | 选择 | 理由 |
|--------|------|------|
| 执行引擎 | ExecutionAgent (DeepAgents) | Agent 理解任务、智能调用 SUT、自适应处理异常 |
| 评估引擎 | PipelineEngine 固定级联 | 评估流程固定，Pipeline 确定性高且无额外 token；LLM-as-judge 内建于 Evaluator |
| SUT 交互方式 | SUT Tools (MCP) | HTTP/CLI/文件操作包装为 MCP Tools，Agent 按需调用 |
| 执行-评估交互 | 文件系统数据包（workspace/） | 简单、可审计、便于复用 |
| 级联编排 | PipelineStage 固定级联 | 默认确定性流程，结果可复现、成本可控 |
| 规则格式 | YAML + JSON Schema | 人可读、Agent 易解析 |
| LLM 接入 | Provider 抽象层 | 屏蔽协议差异 |
| 文档组织 | 总览 + 按架构层次拆分 | 便于维护和扩展 |
| Web Portal | React + Express | 适配腾讯云函数部署，前后端分离 |
| 评估输入 | 支持目录结构 | DirectoryCollector 遍历目录，manifest 记录层级 |
| 评分确定性 | ScoreAggregator 代码执行 | 评分计算始终保持确定性，不依赖 Agent 推理 |
