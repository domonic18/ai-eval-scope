# 评测数据全景与存储梳理

> 本文档梳理 Agent 评测全链路的三类数据——**输入数据**（评测前的配置与资产）、**运行数据**（过程中的过程性数据）、**输出数据**（评测产物）——及其存储位置、敏感分级与改进方向。属于 [01 整体架构设计](./01整体架构设计.md) 的数据视角展开，与 [03 执行引擎设计](./03执行引擎设计.md)、[06 数据管理与配置规范](./06数据管理与配置规范.md)、[13 配置管理设计](./13配置管理设计.md) 互为引用。
>
> 基线：2026-08-25（LLM 配置双形态已实施）。路径以代码实现为准（`config/paths.py` / `storage/workspace.py` / `execution/registry.py`）。

## 一、数据敏感分级（本文档的总纲）

管理方式由**敏感级别**决定，而非「凡凭证皆密钥」：

| 级别 | 数据 | 管理方式 | 行业依据 |
|------|------|---------|---------|
| 🔴 **真密钥** | LLM api_key（计费/泄露有实际损失） | 本地 `~/.agent_eval/llm.json`（0600）/ 平台 DB 加密 + 拉取 | gh / AWS CLI / opencode 的 auth 文件惯例 |
| 🟡 **测试账号**（低敏配置数据） | SUT 登录用户名/密码/验证码（staging 测试账号） | **内联于 sut_config** / 平台 DB 明文——随配置版本化，不进 `.env` | 测试框架共识：fixture 放非敏感测试数据，secrets 只留真密钥；测试账号仅存在于测试环境 |
| 🟠 **运行时会话** | 登录后的 session token/cookie | `workspace/sut_sessions/`（0600）缓存，过期清理；与产物同区——清 workspace 即全新重测 | 运行时产物，集中管理 |
| ⚪ **环境接入** | 平台地址、上报鉴权 | `.env`（本地）/ SCF env（云端） | 12-Factor |

`.env` 的终态职责**只剩环境接入**——不承载 LLM 配置，也不承载 SUT 测试账号。

## 五、已实施：LLM 配置双形态（✅ 2026-08-25）

- **CLI（本地）**：`agent-eval models login/list/test/logout` 交互向导 → `~/.agent_eval/llm.json`（0600，`AGENT_EVAL_LLM_CONFIG` 可覆盖路径）；固定三角色 `text`（评估文本，default）/ `vision`（视觉）/ `agent`（执行侧，回退 text）；规则集 `params.llm_role: vision` 绑定
- **云函数**：平台 `/admin` 按角色配置（`llm_models.role` 列）；executor 经 `GET /api/public/llm-config`（API Key + 限流 + 审计）拉取解密配置，内存持有不落盘——两套实现互不感知
- 解析统一走 `config/llm_resolution.py`（本地文件优先 → 平台拉取兜底）；缓存指纹为解析内容（剔除密钥）；`llm_config.yaml` / `${VAR}` / `.env` LLM key 段均已移除
- 详细规范：[06 §4.8](./06数据管理与配置规范.md)、[05](./05LLM模块设计.md) v2.3

### 六.1 任务集并入场景包（修订 v1.1 三轴决策）

**v1.1 曾裁定**任务集为独立第三轴；**本次修订为两轴 + 内嵌**：场景包（怎么评 + **问什么**）× SUT（问谁）。

**行业对标**（详见调研来源）：

- **lm-evaluation-harness**：task YAML 按 benchmark 套件目录组织（`lm_eval/tasks/mmlu/`…），task 配置内嵌 `dataset_path` 引用与 prompt 模板——考题与评估方法论在同一资产体系、同一版本节奏；自定义任务经 `--include_path` 外挂
- **Inspect AI（UK AISI）**：社区 eval 收录在独立的 `inspect_evals` 仓库，每个 eval 是自包含目录（task 定义 + 数据集一体）
- 共同形态：**「一个场景的评估定义 = 方法论 + 考题」打包分发**，被测对象（model/SUT）是运行时参数

**修订理由**：

1. 任务集天然场景相关（chat 任务与 courseware 任务结构不同），独立目录反而要靠 `scenario` 字段维持弱关联
2. 复用场景包**整条既有链路**：入库评审 → 版本/标签 → `importAssetsToDb` → DB 副本 → 云函数按引用拉取——零新机制
3. 版本一致性：考题与规则的兼容性随包版本共同演进，避免「包 v2 配 task_set 旧版」的失配
4. 三轴中真正需要独立的只有 SUT（环境相关、多对多复用，理由见 §六.2）

**落点**：

```
packages/{scenario}/{ver}/
├── rules/  prompts/  metrics/  datasets/
├── task_sets/                    # ← 新增：包内任务集（考卷）
│   ├── default.yaml              #    缺省考卷（manifest 的 default_task_set 指向）
│   └── regression.yaml
└── agent_eval.yaml               # manifest 增 default_task_set 键
```

- CLI：`agent-eval run --package chat --task-set default`（包内名）；`--task-set <路径>` 显式外挂（保留自定义考卷能力，对齐 `--include_path` 惯例）
- DB：`TaskSetAsset` 新表，**挂 scenario 级**（与场景包资产同构，org 级归属仅 SUT 需要）
- 迁移：`workspace/task_sets/*.yaml` 按其 `scenario` 字段归位到对应包的 `task_sets/`，一次性完成

### 六.2 SUT 测试账号内联 + 注册表资产化

**SUT 为何独立于场景包**（v1.1 决策经评审复议后维持，理由收敛为四点）：

1. **变更域不同**：场景包是评审过的方法论资产（慢变、走 PR）；SUT 端点/modelId/账号随部署走（快变、运维事实）——进包会让每次 staging 重新部署都 bump 包版本，运维噪音灌进方法版本史
2. **复用方向相反**：任务集→场景是 1:1 语义绑定（进包消除弱关联）；SUT→场景是 1:N 横切（同一 SUT 跑多场景），进包即复制 N 份端点+账号
3. **开源边界**：主仓场景包必须零端点信息；任务集天然干净，SUT 必然携带
4. **行业实践**：lm-eval（`--model_args`）/ Inspect（`--model` + 全局 provider 配置）/ HELM 一致把被测对象放运行参数；promptfoo 式「providers 同文件」属单人轻量工具形态，与本系统的版本化/分发形态不同

**边界**：包内 `sut_configs/` 目录保留给 **benchmark 裸模型**（GSM8K 类静态权重，属评测资产、随包分发合理）——与在线被测服务（环境端点）同名异义，arch/13 原设计即此语义。

**修订**（v1.2 曾设计凭证 DB 加密/`credential_ref` env 引用）：评测登录认证（用户名/密码/手机号验证码）属 **staging 测试账号**——行业共识为**非敏感测试数据**（fixtures 放非敏感数据、secrets 只留真密钥；测试账号仅存在于测试环境）。按密钥级管理（`.env` 红线 / AES 加密 / 审计）成本错配。

**落点**：

```yaml
sut:
  name: sasan-agent
  base_url: https://agent-server.staging.example.com
  auth:
    type: api_login
    credentials:            # ← 测试账号内联（低敏配置数据）
      username: "138xxxx0000"
      password: "330330"    # staging 固定验证码
    login: {...}
```

- `credentials` 内联进 `sut_config`；`credential_ref`（env 引用）降级为**可选覆盖**——确有敏感凭证时可指到 env，默认无人需要
- 云端分发不建 DB 通道：executor 镜像构建 COPY `evaluator/` 时自动携带 `sut_systems/`——零新机制
- 会话 token 移至 `workspace/sut_sessions/`（0600 + 过期清理不变）——评测状态集中于 workspace
- 注册表位置：`evaluator/sut_systems/`（仓库内、pip 包外、入库评审）；开源时整体挪出主仓，内部包内只留 example

### 六.3 运行绑定显式化 + 声明式套件

`run_manifest` 记录 `{package_ref(含 task_set), sut_ref}` 及内容指纹；填充 `Run.sutVersion` 与事件 `sut_version`（现状恒空）。`suite.yaml` 声明评测矩阵：

```yaml
suite: sasan-agent-monthly
runs:
  - { package: chat@1.0, task_set: default,      sut: sasan-agent@staging }
  - { package: chat@1.0, task_set: regression,   sut: sasan-agent@staging }
  - { package: chat@1.0, task_set: default,      sut: sasan-agent@prod }
```

（对标 HELM run specs / Inspect 多模型复跑：被测对象是运行参数。）
