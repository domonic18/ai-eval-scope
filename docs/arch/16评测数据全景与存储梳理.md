# 评测数据全景与存储梳理

> 本文档系统梳理 Agent 评测全链路的三类数据——**输入数据**（评测开始前存在的配置与资产）、**运行数据**（评测过程中产生的过程性数据）、**输出数据**（评测产物）——及其存储位置、格式、敏感级别与入库策略，用于评估当前存储方式的合理性并给出改进方向。属于 [01 整体架构设计](./01整体架构设计.md) 的数据视角展开，与 [03 执行引擎设计](./03执行引擎设计.md)、[06 数据管理与配置规范](./06数据管理与配置规范.md)、[13 配置管理设计](./13配置管理设计.md) 互为引用。
>
> 梳理基线：2026-08-24（执行引擎 v4.6.4：commands 形态通道 + chat 场景评估包落地后）。路径均以代码实际实现为准（`config/paths.py` / `storage/workspace.py` / `execution/auth/session.py` / `orchestrator/orchestrator.py`）。

## 一、路径约定总览

| 根 | 定位 | 配置方式 |
|----|------|---------|
| `agent_eval/assets/` | **随 pip 发布的内置资产**（场景包/配置示例/schema），非用户数据 | `PACKAGE_ROOT` 定位 |
| `./workspace/`（CWD 相对） | **用户工作区**（运行产物/缓存/本地配置），不随包发布 | `WORKSPACE_DIR` 环境变量可覆盖 |
| `~/.agent_eval/` | **用户主机级数据**（SUT 会话凭证等敏感文件） | `AGENT_EVAL_SUT_SESSION_DIR` 可覆盖 |
| `.env`（仓库根） | **凭证**（密钥/账号），`.gitignore` 拦截，严禁入库 | `load_dotenv()` 向上查找 |
| Web 平台（PG + COS）+ Langfuse SaaS | **远端存储**（团队共享/追踪） | 上传链路见 [09](./09Web可观测平台架构设计.md) |

## 五、存储方式合理性评估

### 5.1 做得对的

| 实践 | 说明 |
|------|------|
| 凭证三层分离 | 配置（可入库）→ `credential_ref` 间接引用 → env/.env（红线不入库）→ 会话 token 0600 独立于 workspace。配置泄露不等于凭证泄露 |
| 场景包资产化 | 内置包入库 + DB 同步 + 版本标签，chat 场景零机制改动直接复用（[14](./14场景扩展指南.md)） |
| 运行产物按 run_id 隔离 | 日志/结果/证据分层（`RunWorkspace` 约定），可追溯 |
| workspace 与资产分离 | 用户数据（WORKSPACE_DIR）不随包发布，`paths.py` 单一定位源 |

### 5.2 发现的问题（按严重度分级，均为**现状记录**，改进见 §六）

| 级别 | 问题 | 事实与影响 |
|------|------|-----------|
| 🔴 P1 | **执行包布局与 RunWorkspace 约定不一致** | `RunWorkspace` 定义 `runs/{run_id}/packages/{task_id}/`，但 `agent-eval run` 直写 `--output-dir/{task_id}/`：①同 task_id 重跑互相覆盖（staging 调试期间多次手动 `rm -rf` 规避）；②执行包不挂 run_id，与 agent_logs/results 无法关联；③`run_manifest.json` 不登记执行包 |
| 🔴 P1 | **评测定义落在 gitignored workspace** | sut_config（#3）与 task_set（#5）是"考场配置+考卷"，应版本化/评审/复用，现与运行产物混放且不入库——换机器或协作即丢失。根因是当初担心凭证入库；凭证已分离到 env，**配置本身无敏感字段、可入库** |
| 🟡 P2 | **ExecutionPackage 无内容指纹** | agent 产包 `content_hash: null`（仅场景包路径有 hash）→ 评估缓存键失去内容维度，包内容变化仍可能命中旧缓存 |
| 🟡 P2 | **workspace 根目录污染** | CLI 测试产物（如 `workspace/t_cli_1`）、执行包、配置、数据集混放同一层，无约定区分 |
| 🟡 P2 | **LLM 配置双轨割裂** | 一个可用 provider 需 `llm_config.yaml` 条目与 `.env` key 两处配合，缺一即 LLM Judge 整体初始化失败并全部降级（`cli/_common.py:60-62`）；开发者需同时掌握 yaml 格式与 `${VAR}` 引用两套机制。目标态为平台 DB 管理（→ §6.2-四），而非 `.env` 归一 |
| 🟢 P3 | 远端存储无统一数据地图 | Langfuse SaaS（出境合规待确认）/ 平台 PG+COS / 本地 workspace 三处，数据所有权与导出路径未成文 |

### 6.1 SUT 配置的归属决策（v1.1 记录）

**问题**：SUT 配置是否应并入场景包或任务集？——**结论：两者皆不并入，独立注册表 + 运行时绑定。**

三轴正交模型——每轴回答一个独立问题，混并任何两轴都会造成组合爆炸或版本失配：

| 轴 | 回答 | 变更节奏 | 举例 |
|----|------|---------|------|
| 场景包（怎么评） | 评估方法论：规则/提示词/指标 | 随评估方法演进，慢 | chat 场景包 |
| 任务集（问什么） | 考题与预期 | 随评测内容扩充 | sasan-agent-general（3 任务） |
| SUT 配置（问谁） | 被测对象接入：端点/协议形态/鉴权/modelId | 随部署环境变，快 | sasan-agent@staging |

不并入的四个理由：

1. **多对多复用**：同一 SUT 会被多场景评（sasan-agent 现走 chat，后续安全/RAG 场景）；同一场景+任务集评多个 SUT（多模型对比是评估系统的核心价值）。SUT 进场景包 → 包数 = 场景×环境 爆炸。
2. **环境相关性**：base_url/鉴权/modelId 随 staging/prod 切换，与场景包（稳定方法论资产）版本节奏不同；SUT 是**每环境一份的注册表**。
3. **凭证安全边界**：SUT 配置经 `credential_ref` 间接引用 env 凭证；场景包入库分发，绝不能携带接入信息。
4. **与 arch/13 SUTConfig 不冲突**：那是场景包内声明 benchmark 裸模型直连（GSM8K 类）；本表 SUTSystemConfig 是平台级被测系统注册表，服务对象与生命周期均不同。

**但它确实属于"评测任务"**——正确归属是**评测运行定义**（run 的输入绑定），而非场景包/任务集内部。落点即上方 P0"绑定显式化"：run_manifest 记录 `{scenario_package_ref, task_set_ref, sut_name+sut_config 指纹}`，可复现、可对比、可审计。

**决策与落地的差距**（2026-08-24 复核）：

1. **DB 表归属与决策矛盾**：`SUTConfigAsset`（web/backend/prisma/schema.prisma:412）按 `scenarioId` 挂场景、且无任何路由实现——与「SUT 独立于场景」的三轴决策矛盾，资产化时应改挂 org 级（§六-P1）
2. **设计文档残留旧路径**：arch/03 §4.0.3 / arch/13 §4.1 仍写「SUT 配置位置：场景包 `sut_configs/` 或 CLI 显式传入」——需修订对齐三轴决策（现状三个内置包均无 `sut_configs/` 目录，实际只走 CLI 传入 `workspace/sut_configs/`）
3. **SUT 身份未进运行记录**：`run_manifest.json` 仅记 `mode/package_dir/project`；观测事件 `sut_version` 已声明但调用点恒空传——`Run.sutVersion` 实际总是空，即 §六-P0「绑定显式化」的落点
4. **SUT 凭证变量未入模板**：`AGENT_EVAL_SUT__<REF>__{USERNAME|PASSWORD|TOKEN}` 仅在 arch/03 §4.0.3 约定，`.env.example` 无此节（与 §6.2 凭证分层同主题）

### 6.2 配置与用例管理目标架构（v1.2 提案，未实施）

**背景**：针对两点反馈定向设计——① LLM 配置双轨（yaml + env）割裂，但云函数侧未来将以平台 DB 为 LLM 配置真相源，`.env` 归一并非最优解；② 评测管理（SUT / 任务集 / 凭证）才是当前最优先问题。**设计原则：终态设计、一次性切换、不留兼容层**（过渡策略会带来额外的维护与调试成本）。

#### 一、设计哲学（行业对标）

| 原则 | 行业出处 | 本系统落法 |
|------|---------|-----------|
| Eval-as-Code | lm-evaluation-harness / Inspect AI（UK AISI）/ OpenAI Evals：评测定义是仓库内版本化资产，走 PR 评审 | 场景包、任务集、SUT 注册 = 仓库 YAML 资产 |
| 控制面 / 数据面分离 | K8s（etcd 存期望态、kubelet 拉取）、GitHub Actions（workflow + secrets 存服务端、runner 拉取） | 平台 DB = 配置中心（共享/加密/审计）；评测器（云函数）= 无状态 worker，按引用拉取 |
| 凭证与配置分离、密钥托管 | GitHub Org Secrets / Vercel Env：云端加密存储 + 运行时注入，本地 `.env` 同名约定 | 凭证 DB 加密存储，运行时注入进程 env；统一经既有 `CredentialStore` 单点解析 |
| 三轴正交、运行时绑定 | Inspect `eval(task, --model)`：被测对象是运行参数，不是评测内容的组成部分 | 一次 run = 场景包 × 任务集 × SUT 的绑定实例（§6.1） |

#### 二、终态三层配置模型

| 层 | 内容 | 真相源 | 到达评测器 |
|----|------|--------|-----------|
| **评测资产**（怎么评 / 问什么 / 问谁） | 场景包、任务集、SUT 注册表 | 仓库 YAML（评审+版本）→ `importAssetsToDb` → 平台 DB（运行时服务） | 本地 CLI 直读 YAML；云函数按 `名称@版本` 引用从平台拉取 |
| **凭证**（钥匙） | SUT 账号/token、LLM api key | 平台 DB 加密存储（团队共享）；`.env` 同名约定（本地/开源） | executor 启动时拉取解密 → 注入进程 env（不落盘/不入日志/不进 trace） |
| **环境接入** | 平台地址、上报鉴权、基础设施连接 | `.env`（本地）/ SCF env（云端） | 进程 env（现状不变） |

开发者终态视图：`.env` 只剩环境接入类变量，**不再承载任何 LLM/SUT 业务配置**——新增用例在资产目录加 YAML 提 PR，换 LLM 在平台 admin UI，接入新 SUT 在资产仓加注册文件 + 平台录入凭证。

#### 三、最优先：评测管理（P0）

1. **任务集资产化**：YAML 迁入分层资产目录（TaskSet schema 已有 `scenario` 字段），复用场景包「入库 → `importAssetsToDb` → DB 版本标签」既有链路，零新机制；`workspace/task_sets/` 现存实配一次性迁入
2. **SUT 注册表资产化**：真实端点入私有资产仓 / 平台 DB；**开源主仓库只入 example 模板**（`assets/examples/`，现 `sut_config.example.yaml` 归位于此）——真实端点入库 = 开源日的内网地址泄露事故
3. **凭证 DB 化**：复用 `llm_models.apiKeyEncrypted` 同款加密设施（`PLATFORM_KEY_ENCRYPTION_KEY`）；`credential_ref` 从「指向 env 变量」升级为「指向平台凭证记录」；本地开发同约定走 `.env`（变量补进 `.env.example`，见 §6.1-差距4）；会话 token 缓存 `~/.agent_eval/` 0600 机制不变
4. **运行绑定显式化 + 声明式套件**：`run_manifest` 记录 `{scenario_package_ref, task_set_ref, sut_ref}` 及各自内容指纹；填充 `Run.sutVersion` 与事件 `sut_version`；新增 `suite.yaml` 表达「不同评测地址 × 不同任务集」的矩阵（一次声明、批量展开、统一对照）：

```yaml
# suite.yaml —— 声明式评测矩阵（开源形态的核心用户界面）
suite: sasan-agent-monthly
runs:
  - { task_set: sasan-agent-general@1.0, sut: sasan-agent@staging }
  - { task_set: safety-core@0.3,        sut: sasan-agent@staging }
  - { task_set: sasan-agent-general@1.0, sut: sasan-agent@prod }
  - { task_set: sasan-agent-general@1.0, sut: competitor-a@default }   # 多模型对比
```

#### 四、次优先：LLM 配置方向记录（非本轮实施）

- 真相源 = 平台 DB `llm_models`（admin CRUD / 连通性测试 / 设默认**均已实现**）
- 评测器运行时经既有 `AGENT_EVAL_HOST/API_KEY` 通道拉取解析后配置；本地开发连本地平台栈（`make docker-up`）
- `llm_config.yaml`、`${VAR}` 引用机制、`export-yaml` 端点**一次性移除**（无兼容层）；缓存指纹从「yaml 文件字节」改为「拉取内容指纹」

#### 五、分层资产目录与开源适配

```text
层1 框架内置（开源主仓库，随 pip 发布）    agent_eval/assets/{packages, task_sets, schemas, examples}/
层2 团队/用户资产仓（独立 git，可私有）     eval-assets/{packages, task_sets, sut_systems}/   ← 结构与层1同构
层3 本机运行时                            .env（凭证 + 平台接入） + ~/.agent_eval/（会话 token）
平台 DB（可选增强）                        importAssetsToDb 同步层2 → 团队共享、云函数拉取
```

- **解析优先级一行规则**（三轴通用，复用现有 `--llm-config > CWD > 包内` 发现惯例）：显式路径参数 > `--assets-dir` 资产仓 > CWD > 框架内置
- **目录同构**：各层 `packages/ task_sets/ sut_systems/` 同名同 schema，校验/导入/发现工具链对任意层通用，用户从 example 复制即得合法资产
- **零平台可用**：开源用户层1 + 层2 + `.env` 即可完整跑评测（CLI 直读 YAML），平台是可选增强而非依赖（lm-eval 之于 Langfuse/W&B 的关系）

#### 六、一次性切换清单（cutover，非过渡）

包内 `llm_config.yaml` 删除、CI fixture 改 `monkeypatch.setenv`、`workspace/{sut_configs,task_sets}` 迁入资产目录后清空、`SUTConfigAsset` 表迁移与 `importAssetsToDb` 扩展，在一条 PR 内完成——不留任何双读/兼容分支。
