# 执行引擎设计

> 本文档详细阐述执行引擎的设计，核心变更为：执行引擎全面采用 **Agent-Driven** 架构，ExecutionAgent（基于 **DeepAgents（Python）** 开源 Agent 框架，模型经 `llm_config` 桥接双协议）端到端驱动评测执行流程，SUT 交互工具以 **LangChain Tool 显式绑定**（MCP 为可选封装）。属于 [01 整体架构设计](./01整体架构设计.md) §二中"执行引擎"的详细展开。

---

## 一、职责边界

执行引擎负责**驱动被测 Agent 运行并采集结果**，不涉及任何评估逻辑：

| 组件 | 职责 |
|------|------|
| **ExecutionAgent** | 基于 DeepAgents（Python，开源、双协议模型无关），端到端驱动执行流程：理解任务、调用 SUT Tools、处理错误、收集结果、生成 ExecutionPackage |
| **SUTToolServer** | 提供 MCP Tools（HTTP 调用、CLI 执行、目录扫描、文件读取、结果收集等），供 ExecutionAgent 调用 |
| **DirectoryCollector** | 遍历目录结构、收集 HTML 文件、生成目录清单。位于 `storage/collector.py`，数据模型定义于 `storage/package.py`，通过 `scan_directory` MCP Tool 暴露给 Agent |
| **TaskSetBuilder** | 任务集构建工具（从零创建 / LLM 半自动生成） |

> **架构变更说明**：传统设计中的 ExecutionEngine + SUTDriver（HTTPDriver/CLIDriver/AgentSUTDriver）分层架构已被 ExecutionAgent + SUT Tools 的 Agent-Driven 架构取代。HTTPDriver/CLIDriver 的逻辑不再作为独立的 Driver 类存在，而是下沉为 SUTToolServer 中的 `invoke_http_sut` 和 `invoke_cli_sut` MCP Tool。ExecutionAgent 根据任务描述智能选择并调用合适的 Tool。
>
> **通道决策（v4.4 定向 / v4.5 收敛，2026-08-18）**：对接的被测系统为多个、且各自有登录鉴权机制。经通道选型评审先裁剪浏览器通道（API 先行，v4.4），后确认**全部对接系统均实现 [Agent Protocol](https://langchain-ai.github.io/agent-protocol/api.html)（v0.1.6，LangGraph Platform 为其超集）**——本期唯一排期通道为 **AgentProtocolChannel**（§4.0.6），`GenericHttpChannel` 与 `BrowserChannel` 均**预留不排期**（`SUTChannel` 抽象保证按需增补实现类即可）。同时新增**通道与鉴权架构**（§4.0）：AuthProvider/SUTSession/SUTRegistry 等组件解决多系统登录、会话复用与凭证安全——协议规范**不含鉴权**，该层必须自建。

### 2.1 RunMode — 运行模式

```python
class RunMode(str, Enum):
    RUN_ONLY = "run-only"
    EVAL_ONLY = "eval-only"

```

**模式说明**：

| 模式 | 行为 |
|------|------|
| `RUN_ONLY` | 仅执行被测 Agent（ExecutionAgent），不进行评估 |
| `EVAL_ONLY` | 仅对已有输出进行评估，不驱动 SUT |
| `PIPELINE` | 依次执行 SUT 驱动和评估。执行阶段由 **ExecutionAgent**（DeepAgents 底座，双协议模型无关）完成，评估阶段由 **PipelineEngine** 完成 |

```python
class Task(BaseModel):
```

## 三、ExecutionAgent — Agent 驱动执行

### 3.1 设计理念

传统执行引擎采用 ExecutionEngine + SUTDriver 分层架构：引擎调度 Driver，Driver 机械地渲染模板、发送请求、解析响应。这种方式在简单场景下工作良好，但面对以下挑战时力不从心：

- **任务多样性**：不同 SUT 的接口格式、认证方式、错误模式各不相同，硬编码逻辑难以覆盖
- **错误恢复**：网络超时、服务降级、参数不匹配等问题需要智能判断和处理策略
- **上下文理解**：某些任务需要理解任务描述的语义，动态调整请求构造方式

**Agent-Driven 方案的核心思想**：将执行控制权交给一个理解任务语义的智能 Agent（基于 DeepAgents（Python）开源框架，模型经 `llm_config` 桥接双协议——模型无关），由 Agent 根据任务描述自主决定调用哪些 SUT Tools、如何构造请求参数、遇到错误时如何重试或降级，最终生成结构化的 ExecutionPackage。

**与传统方案的对比**：

| 维度 | 传统 ExecutionEngine + SUTDriver | Agent-Driven ExecutionAgent |
|------|----------------------------------|------------------------------|
| 执行控制 | 代码硬编码的固定流程 | Agent 理解任务后自主决策 |
| 请求构造 | Jinja2 模板变量替换 | Agent 理解任务语义后智能构造 |
| 错误处理 | 预定义的重试/超时策略 | Agent 根据错误类型动态决策 |
| 结果收集 | 固定的文件复制/解析逻辑 | Agent 调用 scan_directory / collect_results 灵活收集 |
| 适应性 | 新 SUT 需编写新 Driver | 新 SUT 只需配置 Tool 参数 |
| 可观测性 | 日志记录 | 完整的 Agent 会话记录（所有决策过程可见） |

### 3.2 核心类

```python
from deepagents import DeepAgent                      # [agent] optional extra，惰性导入
from agent_eval.agent.model_bridge import build_chat_model   # llm_config → LangChain ChatModel（双协议桥接）
from agent_eval.agent.session import WorkspaceCheckpointer   # 自定义 checkpointer：会话状态落盘 workspace


class ExecutionAgent:
    """基于 DeepAgents（Python）的执行 Agent，端到端驱动评测执行流程（v4.6 底座）。

    - 模型：llm_config.yaml provider → build_chat_model() 构造 LangChain ChatModel
      （ChatOpenAI / ChatAnthropic，双协议 base_url 可配——模型无关）
    - 工具：SUT Tools 经 LangChain Tool 显式绑定（白名单），未绑定的内置工具不可用
    - 预算：BudgetGuard 以 LangGraph 回调注入（on_llm_end 累计 token/成本，超限终止）
    - 状态：WorkspaceCheckpointer 将会话状态外部化落盘（推理-执行-状态分离，SCF 友好）
    """

    def __init__(self, config: AgentConfig, sut_tools: SUTToolServer):
        self.config = config
        self.sut_tools = sut_tools
        self.agent = DeepAgent(
            model=build_chat_model(config.llm_provider),
            tools=sut_tools.to_langchain_tools(),               # §四 工具显式绑定
            system_prompt=EXECUTION_SYSTEM_PROMPT,              # §3.3
            checkpointer=WorkspaceCheckpointer(config.workspace_dir),
            config={"recursion_limit": config.max_turns * 2},   # 轮次限制（防无限循环）
        )
        self.agent.add_callbacks([BudgetGuard(config.max_budget_usd)])

    async def run_task(self, task: Task) -> ExecutionPackage:
        """执行单个任务，返回 ExecutionPackage。"""
        result = await self.agent.ainvoke(
            {"messages": [{"role": "user", "content": self._build_task_prompt(task)}]},
            config={"configurable": {"thread_id": task.task_id}},
        )
        session = AgentSession.from_messages(result["messages"])
        return self._build_package(session, task)

    async def run_task_set(self, task_set: TaskSet) -> list[ExecutionPackage]:
        """批量执行任务集，返回执行包列表。"""
        return [await self.run_task(task) for task in task_set.tasks]

    def _build_package(self, session: AgentSession, task: Task) -> ExecutionPackage:
        """从 Agent 会话记录构建 ExecutionPackage。"""
        # 解析 Agent 最终输出（write_package 工具产物），提取 ExecutionPackage 结构
        ...
```

**底座集成要点（v4.6）**：

| 集成点 | 方案 |
|--------|------|
| 模型接入 | `build_chat_model(llm_provider)`：读 `llm_config.yaml`（[05](./05LLM模块设计.md)），按协议构造 `ChatOpenAI`（OpenAI 兼容）或 `ChatAnthropic`（Anthropic 兼容），带 `base_url`/`api_key`/`model`——**执行 Agent 与评估 LLM 共用同一配置源** |
| 工具绑定 | SUTToolServer 工具导出为 LangChain Tool（`@tool` 装饰或 StructuredTool.from_function）显式传入；DeepAgents 内置工具（filesystem/子 Agent 等）按需保留（规划 Todo、压缩默认开启，文件操作仅保留其虚拟 FS 与 `write_package` 的衔接） |
| 预算控制 | BudgetGuard 实现 LangGraph 回调（`on_llm_end` 累计 token → 成本估算，超 `max_budget_usd` 抛 `BudgetExceededError` 终止图执行） |
| 会话状态 | WorkspaceCheckpointer（LangGraph BaseCheckpointSaver 实现）落 `workspace/agent_sessions/`，崩溃可恢复、可重放、可审计；SCF 部署时换 PG/COS 实现（PoC 验证项） |
| 上下文压缩 | DeepAgents 内置压缩能力直接受益（SUT 大产物回填场景），无需自研 |
| 依赖管理 | `deepagents` + `langgraph` 放 evaluator `[agent]` optional extra（仿 playwright 惰性导入惯例），未安装时 CLI 给出友好提示 |

### 3.3 System Prompt 构建

System Prompt 引导 ExecutionAgent 理解自身角色和执行规则：

```python
def _build_system_prompt(self, task: Task) -> str:
    return f"""你是一个评测执行 Agent（ExecutionAgent），负责驱动被测系统（SUT）执行任务并收集结果。

## 你的职责
1. 理解任务描述，确定需要调用的 SUT 交互方式
2. 构造正确的请求参数，调用合适的 SUT Tool
3. 检查响应是否成功，如遇错误则智能重试或降级
4. 收集执行结果文件，生成目录清单（如适用）
5. 将最终的 ExecutionPackage 写入 workspace

## 可用工具
{self.sut_tools.describe_tools()}

## 执行规则
- 每个任务必须在 {self.config.max_turns} 轮内完成
- 遇到超时或服务错误时，最多重试 {self.config.max_retries} 次
- 必须在任务结束时调用 write_package 写入执行包
- 如果 SUT 交互失败且无法恢复，写入包含错误信息的执行包

## 输出规范
- 所有输出文件必须写入指定 workspace 目录
- 目录模式任务需调用 scan_directory 生成清单
"""
```

### 3.4 Task Prompt 构建

Task Prompt 提供具体的任务信息，供 Agent 理解并执行：

```python
def _build_task_prompt(self, task: Task) -> str:
    prompt_parts = [
        f"## 任务 ID: {task.id}",
        f"## 任务输入",
        json.dumps(task.input, ensure_ascii=False, indent=2),
    ]
    if task.expected:
        prompt_parts.append(f"## 预期结果\n{json.dumps(task.expected, ensure_ascii=False, indent=2)}")
    if task.constraints:
        prompt_parts.append(f"## 约束条件\n{json.dumps(task.constraints, ensure_ascii=False, indent=2)}")

    # 目录模式
    if task.input_mode == "directory" and task.directory_path:
        prompt_parts.extend([
            f"## 目录模式",
            f"- 目录路径: {task.directory_path}",
            f"- 文件匹配模式: {task.file_patterns}",
            f"请先调用 scan_directory 扫描目录结构，然后收集结果文件。",
        ])

    prompt_parts.append("请执行上述任务，并在完成后调用 write_package 写入执行包。")
    return "\n\n".join(prompt_parts)
```

### 3.5 Agent 会话管理

ExecutionAgent 通过 DeepAgents 的 `ainvoke` 迭代运行整个会话生命周期（每轮：LLM 决策 → 工具执行 → 结果回填，直至产出 `write_package` 或触顶），会话状态经 LangGraph checkpointer 外部化落盘（推理-执行-状态分离）：

```python
@dataclass
class AgentSession:
    """Agent 会话记录，保存完整的交互历史。"""
    messages: list[dict]             # 所有消息（用户提示、工具调用、工具结果、Agent 响应）
    total_input_tokens: int = 0      # 输入 token 总量
    total_output_tokens: int = 0     # 输出 token 总量
    tool_call_count: int = 0         # 工具调用次数
    started_at: str = ""             # 会话开始时间
    finished_at: str = ""            # 会话结束时间
```

会话管理的关键机制：

| 机制 | 说明 |
|------|------|
| **消息追踪** | 记录 Agent 的每一步决策和工具调用，支持事后审计 |
| **Token 计量** | 统计输入/输出 token，用于成本控制和预算管理 |
| **轮次限制** | `max_turns` 防止 Agent 无限循环 |
| **预算控制** | `max_budget_usd` 硬性限制单任务花费上限 |

### 3.6 预算控制

```python
class BudgetController:
    """预算控制器，监控 Agent 执行成本。"""

    def __init__(self, max_budget_usd: float, warn_threshold: float = 0.8):
        self.max_budget_usd = max_budget_usd
        self.warn_threshold = warn_threshold
        self.spent_usd = 0.0

    def check(self) -> str:
        """检查当前预算状态。

        Returns:
            "ok" | "warning" | "exceeded"
        """
        if self.spent_usd >= self.max_budget_usd:
            return "exceeded"
        elif self.spent_usd >= self.max_budget_usd * self.warn_threshold:
            return "warning"
        return "ok"
```

## 四、SUT Tools（MCP）— SUT 交互工具

SUTToolServer 以 MCP Server 形式为 ExecutionAgent 提供与被测系统交互的工具集。传统 HTTPDriver/CLIDriver 的逻辑下沉到这些工具中，由 Agent 根据任务描述自主选择调用。

> **v4.6 工具形态调整**：随底座切换（§三），工具不再依赖 MCP 形态——`SUTToolServer` 演进为**工具注册表**，工具导出为 LangChain Tool（名称/描述/JSON Schema/函数）显式绑定给 DeepAgents。MCP 封装保留为**可选能力**（外接独立 MCP Server 的工具场景），不再是必需路径。

### 4.0 通道与鉴权架构（v4.4 新增）

**背景**：v4.3 的 `invoke_http_sut` 假设"单系统、无鉴权、接口已知"（headers 静态传入、`httpx.AsyncClient` 每请求新建即弃），而实际对接的**多个被测系统各自有登录鉴权机制**。缺五项能力：登录流程编排、会话（token/cookie）获取与跨任务复用、过期自动重登、多系统配置管理、凭证安全。本节补齐该层。

**通道决策**：已确认**全部对接系统实现 Agent Protocol**（v0.1.6）。本期唯一排期通道为 **AgentProtocolChannel**（§4.0.6）；`GenericHttpChannel`（§4.2 `invoke_http_sut` 模板模式，服务非协议系统）与 `BrowserChannel`（Playwright，UI-only 兜底 + 截图挂接 VisionEvaluator）均**预留不排期**——`SUTChannel` 抽象保证后续按需增补实现类，不影响鉴权层与本层其余组件。

#### 4.0.1 组件抽象

| 组件 | 职责 | 位置（规划） |
|------|------|------|
| **SUTChannel** | 通道抽象：统一"向被测系统发起一次交互"的语义（发送请求/挂载会话/判定会话失效）。本期实现 `AgentProtocolChannel`（§4.0.6，全部对接系统走此通道）；`GenericHttpChannel` / `BrowserChannel` 预留 | `agent_eval/execution/channels/` |
| **AuthProvider** | 登录引导：按 sut_config 的 `auth` 策略完成登录 → 产出 `SUTSession`；负责会话过期检测与自动重登（含频次限制） | `agent_eval/execution/auth/` |
| **SUTSession** | 会话产物：token / cookie jar + 过期时间；进程内缓存 + 落盘持久化（跨运行复用，避免每次评测重新登录触发风控） | 同上 |
| **SUTRegistry** | 多系统注册表：加载 `sut_configs/` 下多份 sut_config，按 `sut.name` 索引；提供系统清单与健康检查（登录探活） | `agent_eval/execution/registry.py` |
| **CredentialStore** | 凭证读取：仅从环境变量 / `.secret` 文件注入；sut_config 只存 `credential_ref` 引用。**凭证本体与会话产物严禁入库** | 同上 |

#### 4.0.2 鉴权策略（`auth.type`）

| type | 流程 | 适用 |
|------|------|------|
| `none` | 不鉴权，直接请求 | 内网无鉴权服务 |
| `static_token` | 静态 token/API Key（env 注入），长期有效 | **首选**——系统方可直接提供长期测试 token（最稳，无登录环节） |
| `api_login` | 登录 API 模板：POST 账密（Jinja2 渲染）→ 按提取规则从响应取 token → 后续请求自动挂载 → 过期自动重登 | 系统有登录接口、无验证码/风控 |
| `session_cookie` | 登录后以 cookie 会话：cookie jar 持久化复用，过期重登 | 登录态在 cookie 的传统 web 系统 |

> 浏览器登录（`storage_state` 持久化 + 验证码人工介入钩子）属 BrowserChannel 范畴，随其立项再入表。

#### 4.0.3 sut_config.yaml v2（多系统 + 鉴权）

一份 config 描述**一个**被测系统，多系统即多份文件；位置：场景包 `sut_configs/<system>.yaml`（`assets/packages/<scenario>/<package>/<version>/sut_configs/`，见 [06 §1.3](./06数据管理与配置规范.md)）或 CLI 显式传入，`SUTRegistry` 聚合加载。

> 本节示例为 **GenericHttpChannel（预留通道）** 的 config 形态；本期主通道 `agent_protocol` 的 config 见 §4.0.6-c。

```yaml
sut:
  name: "courseware-agent"            # 系统标识（SUTRegistry 索引键，全局唯一）
  channel: generic_http               # generic_http（预留）| agent_protocol（本期主通道，§4.0.6）| browser（预留）
  base_url: "https://agent.example.com"
  timeout: 120

  auth:
    type: api_login                   # none | static_token | api_login | session_cookie
    credential_ref: "COURSEWARE_AGENT"  # 凭证引用——实际账密/token 经 env 注入（见下），严禁写在本文
    login:                            # type=api_login 时必填
      method: POST
      path: "/api/login"
      body_template: '{"username": "{{ username }}", "password": "{{ password }}"}'
    extract:                          # 从登录响应提取会话凭证
      token_path: "data.access_token"     # JSON path
      token_type: "Bearer"                # Bearer | cookie | header:<HeaderName>
      expires_in_path: "data.expires_in"  # 秒数；缺省用固定 TTL（默认 3600）
    mount:                            # 业务请求自动挂载方式
      header: "Authorization"             # 与 token_type=Bearer/header:X 配合；cookie 型则挂 cookie jar

  request_template:                   # 业务请求模板（同 v1，Jinja2 渲染任务参数）
    method: POST
    path: "/generate"
    body:
      subject: "{{task.input.subject}}"

  response_mapping:                   # 响应字段映射（同 v1）
    success_field: "success"
    output_files_field: "output_files"
```

**凭证 env 注入约定**（复用 `.secret/.env` 惯例，见 [06 §4.6](./06数据管理与配置规范.md)）：

```
AGENT_EVAL_SUT__<NAME>__USERNAME=...   # api_login / session_cookie 用
AGENT_EVAL_SUT__<NAME>__PASSWORD=...
AGENT_EVAL_SUT__<NAME>__TOKEN=...      # static_token 用
```

sut_config 中出现明文密码/token 属**安全红线违规**（等同密钥入库，CI/评审拦截）。

#### 4.0.4 会话生命周期

1. **首请求前**：`AuthProvider` 检查会话缓存（内存 → 落盘 `sessions/` 目录，位于 workspace 之外、gitignore、权限 600）；
2. **无会话/已过期** → 执行登录（渲染账密 env → 请求登录接口 → 提取凭证）→ `SUTSession` 落盘；
3. **业务请求**：经该系统 `SUTSession` 绑定的共享 `AsyncClient`（连接池 + cookie jar 复用）自动挂载凭证——同一运行内多任务**不重复登录**；
4. **命中 401/403** → 判定会话失效 → 自动重登**一次**并重放请求；重登设频次上限（默认每系统每 30 分钟 ≤ 1 次，超限报 `SUTAuthError`），防自动化登录触发风控锁号；
5. **运行结束**：会话默认保留复用（长会话系统收益最大）；config 可声明 `auth.logout_on_finish: true` 显式登出。

#### 4.0.5 安全要求

- 凭证仅经 env/`.secret` 注入，sut_config 只存 `credential_ref`；
- `SUTSession` 落盘文件（token/cookie）**等同凭证**：workspace 外存储、gitignore、600 权限、过期自动清理；
- Agent 会话日志与错误信息对 `Authorization`/`Cookie`/token 值脱敏（复用平台 API Key 脱敏惯例：`Bearer eyJh***`）；
- 建议每个被测系统使用**专用测试账号**，与生产账号隔离。

### 4.0.6 Agent Protocol 通道（本期唯一排期通道）

**适用性**：已确认全部对接系统均实现 [Agent Protocol](https://langchain-ai.github.io/agent-protocol/api.html)（v0.1.6）。协议已把端点、状态机、输入输出模型标准化——per-system 的 request_template/response_mapping 定制需求消失，仅剩**鉴权（§4.0.2）**与**产出物提取**两处系统差异由 config 声明。

**协议要点**（影响本设计的契约子集）：Run 无状态执行 `POST /runs/wait`（阻塞）/ `POST /runs/stream`（SSE）；后台执行 `POST /runs` → `GET /runs/{id}/wait` / `cancel(action=interrupt|rollback)`；Threads 多轮（**每 thread 同时仅一个活跃 run**，否则 409）；`RunStatus: pending | success | error | timeout | interrupted`（**无 running**，pending 直达终态）；输出 `RunWaitResponse = {run, values, messages}`；能力发现 `POST /agents/search` + `GET /agents/{id}/schemas`（input/output/state/config JSON Schema + `capabilities: ap.io.messages / ap.io.streaming`）；错误 `ErrorResponse {code, message, metadata}`；StreamMode `values | messages | updates | custom`。

#### a. 执行模式（`exec_mode`）

| exec_mode | 协议调用序列 | 适用 |
|---|---|---|
| `wait`（默认） | `POST /runs/wait` | 单轮任务，阻塞至终态——**评估默认形态**（隐式临时 thread + `on_completion=delete`） |
| `background` | `POST /runs` → `GET /runs/{id}/wait`；超时则 `POST /runs/{id}/cancel(action=interrupt)` | 长任务 / 需取消能力 |
| `stream` | `POST /runs/stream`（带 `stream_mode`） | 需过程数据（messages/updates 流，过程指标数据源） |

#### b. 语义工具面（取代手搓 HTTP 请求）

Agent Protocol 系统不使用 `invoke_http_sut`（该工具属 GenericHttpChannel 预留），改用协议语义级 MCP Tools：

| MCP Tool | 封装的协议调用 |
|---|---|
| `agent_run(input, exec_mode?)` | `runs/wait`（短）或 `POST /runs`+`wait`（长），返回终态 + values/messages |
| `agent_run_stream(input, stream_mode)` | `runs/stream`，SSE 容错聚合为完整输出 + 过程事件列表 |
| `create_thread / run_on_thread(thread_id, input)` | Threads 多轮任务（对话式课件生成等） |
| `cancel_run(run_id, action)` | 我方超时/预算超限时的主动取消（interrupt / rollback） |
| `get_agent_info(agent_id?)` | `/agents/search` + `/agents/{id}/schemas` 能力与 schema 发现（接入自检用） |

#### c. sut_config（agent_protocol 形态）

```yaml
sut:
  name: "courseware-agent"
  channel: agent_protocol
  base_url: "https://agent.example.com"
  protocol_version: "0.1.6"        # 各系统实现版本可能不一，显式记录（超集实现如 LangGraph Platform 忽略未知字段）
  agent_id: null                   # 缺省用服务默认 agent
  exec_mode: wait                  # wait | background | stream
  stream_mode: messages            # exec_mode=stream 时：values|messages|updates|custom
  auth: { ... }                    # §4.0.2 不变（协议不含鉴权；static_token 首选）
  output_paths:                    # 从 RunWaitResponse 提取产出物（取代 response_mapping）
    files_field: "values.output_files"
    text_field: "values.content"
  on_completion: delete            # 评估场景默认 delete（临时线程用完即删）
```

#### d. 状态机映射（固定表）

| 协议 RunStatus | → 执行引擎状态 | 处理 |
|---|---|---|
| `success` | success | 按 `output_paths` 从 values/messages 提取进 ExecutionPackage |
| `error` | failed | `ErrorResponse.code/message` 进 ExecutionTrace |
| `timeout` | failed(timeout) | 与我方超时区分：SUT 自报超时 vs 我方主动 cancel |
| `interrupted` | interrupted | 人机协作中断，标记待处理（本期不自动恢复） |
| `pending` 持续 | running → cancel | 超过 exec 超时 → `cancel(action=interrupt)` |

#### e. 并发与线程策略

每 thread 单活跃 run（409 约束）→ 评测任务默认走无状态 run（规避并发冲突）；仅多轮对话任务显式 `create_thread`。`run.metadata` 携带 `{eval_run_id, task_id, sut_name}`，便于被测系统侧审计与限流豁免协商。

#### f. 能力自检（SUTRegistry 接入检查）

接入时执行：`POST /agents/search` → `GET /agents/{id}/schemas` → 校验①`capabilities`（threads/messages/streaming 支持度 vs config 所需）；②`input_schema` vs 任务集参数结构；③`output_schema` vs `output_paths` 有效性。结果（含 `protocol_version`）缓存进注册表，自检失败拒绝接入并给出明确缺口报告。

#### g. 流事件容错

协议将各 stream mode 的**事件细节留给实现者**（官方 roadmap 明示）→ 聚合器规则：未知事件**原样写入 ExecutionTrace**（不解析失败、不丢弃）；语义聚合仅依赖"run 终态事件"+ 可选 messages 顺序拼接；SSE 解析容错（缺 `id`/`event` 字段按 data-only 兜底）。

#### h. 风险与对策

| # | 风险 | 对策 |
|---|---|---|
| R1 | 协议**子集实现**（Threads/Agents 阶段可选未实现，`thread_id` 会被忽略） | 能力自检（§f）强制拦截，config 声明所需最低能力 |
| R2 | 流事件各系统不统一 | 容错聚合（§g），未知事件入 trace |
| R3 | 协议早期版本漂移（v0.1.6）；LangGraph Platform 为超集（有私有扩展） | config 记 `protocol_version`；client 按版本适配；未知字段忽略不报错 |
| R4 | `values` 结构每系统不同（由各 agent 的 output_schema 定义） | `output_paths` 必配 + 接入自检时按 output_schema 校验 |
| R5 | `pending` 无运行中状态可观察，长任务挂死 | `exec_mode=background` + 我方超时 → `cancel(interrupt)`；`rollback` 仅在系统声明支持时使用 |

### 4.2 invoke_http_sut — HTTP 请求工具

继承原 HTTPDriver 的核心能力：Jinja2 模板渲染、请求发送、响应映射。Agent 传入任务参数，工具负责渲染模板并发送请求。

```python
@mcp_tool(name="invoke_http_sut", description="发送 HTTP 请求到 SUT（支持 Jinja2 模板渲染）")
async def invoke_http_sut(
    method: str,                          # HTTP 方法（GET/POST/PUT）
    url: str,                             # 请求 URL
    headers: dict = None,                 # 自定义请求头
    body_template: str = None,            # 请求体模板（Jinja2 格式）
    template_vars: dict = None,           # 模板变量（用于渲染 body_template）
    response_mapping: dict = None,        # 响应字段映射规则
    timeout: float = 120,                 # 超时时间（秒）
) -> dict:
    """
    发送 HTTP 请求到被测 Agent 服务。

    1. 如果提供 body_template + template_vars，使用 Jinja2 渲染请求体
    2. 发送 HTTP 请求（带超时控制）
    3. 如果提供 response_mapping，按映射规则提取输出字段
    4. 返回结构化响应

    示例：
      body_template = '{"subject": "{{ subject }}", "grade": "{{ grade }}"}'
      template_vars = {"subject": "数学", "grade": "七年级"}
      → 渲染结果: '{"subject": "数学", "grade": "七年级"}'
    """
    from jinja2 import Template

    # 渲染请求体
    if body_template and template_vars:
        template = Template(body_template)
        body = template.render(**template_vars)
    else:
        body = body_template

    # 发送请求
    async with httpx.AsyncClient(timeout=timeout) as client:
        response = await client.request(
            method=method, url=url, headers=headers,
            content=body,
        )

    # 映射响应字段
    result = {"status_code": response.status_code, "raw": response.text}
    if response_mapping:
        parsed = response.json()
        for target_field, source_path in response_mapping.items():
            result[target_field] = _extract_by_path(parsed, source_path)

    return result
```

**配置迁移说明**：

| 原 HTTPDriver 配置 | invoke_http_sut 对应参数 |
|---------------------|--------------------------|
| `base_url` | `url` 参数 |
| `headers` | `headers` 参数 |
| `request_template.body` | `body_template` + `template_vars` |
| `response_mapping` | `response_mapping` |
| `timeout` | `timeout` |
| `retries` | 由 ExecutionAgent 自行决定重试策略 |

> **v4.4 行为增强**（配合 §4.0 通道与鉴权架构，签名新增可选参数 `system: str = None`、`stream: bool = False`）：
>
> 1. **会话复用**——请求不再每次新建 `AsyncClient`：按 `system` 参数（缺省按 `url` 前缀匹配 SUTRegistry）解析目标系统，使用该系统 `SUTSession` 绑定的共享客户端（连接池 + cookie jar），同一运行内多任务不重复登录；
> 2. **凭证自动挂载**——`auth.mount` 声明的鉴权头/cookie 由 `HttpChannel` 注入；Agent 传入的 `headers` **不含凭证**（防凭证泄漏进 Agent 会话日志），检测到凭证字段则剔除并告警；
> 3. **流式响应聚合**——`stream=true` 时对 SSE/chunked 响应按"终帧到达或超时"聚合为完整文本再返回（web Agent 普遍流式输出，评估器需要完整产物）；
> 4. **会话失效自愈**——命中 401/403 时由 AuthProvider 自动重登并重放一次（对 Agent 透明，仅记录于结构化日志）。
>
> **v4.5 归属说明**：本工具属 **GenericHttpChannel（预留，不排期）**——全部对接系统实现 Agent Protocol，协议系统使用 §4.0.6-b 的语义工具面（`agent_run` 等），不使用本工具。

### 4.3 invoke_cli_sut — CLI 执行工具

继承原 CLIDriver 的能力，通过子进程调用本地 CLI Agent。

```python
@mcp_tool(name="invoke_cli_sut", description="执行 CLI 命令调用本地 SUT")
async def invoke_cli_sut(
    command: str,                         # 完整的 CLI 命令
    working_dir: str = None,              # 工作目录
    env_vars: dict = None,                # 环境变量
    timeout: float = 120,                 # 超时时间（秒）
) -> dict:
    """
    通过子进程执行 CLI 命令调用被测 Agent。

    返回:
      {"exit_code": int, "stdout": str, "stderr": str}
    """
    import asyncio

    proc = await asyncio.create_subprocess_shell(
        command,
        stdout=asyncio.subprocess.PIPE,
        stderr=asyncio.subprocess.PIPE,
        cwd=working_dir,
        env={**os.environ, **(env_vars or {})},
    )
    try:
        stdout, stderr = await asyncio.wait_for(
            proc.communicate(), timeout=timeout
        )
        return {
            "exit_code": proc.returncode,
            "stdout": stdout.decode(),
            "stderr": stderr.decode(),
        }
    except asyncio.TimeoutError:
        proc.kill()
        return {"exit_code": -1, "stdout": "", "stderr": f"命令执行超时（{timeout}秒）"}
```

### 4.5 collect_results — 结果收集工具

```python
@mcp_tool(name="collect_results", description="收集执行结果文件到 workspace")
async def collect_results(
    source_paths: list[str],              # 源文件/目录路径列表
    workspace_dir: str,                   # 目标 workspace 目录
    task_id: str,                         # 任务 ID（用于组织输出目录）
) -> dict:
    """
    将源文件/目录复制到 ExecutionPackage 的 output 目录。

    目录结构：
      {workspace_dir}/{task_id}/output/    ← 输出文件
      {workspace_dir}/{task_id}/_manifest.json  ← 目录清单（如适用）
    """
    output_dir = Path(workspace_dir) / task_id / "output"
    output_dir.mkdir(parents=True, exist_ok=True)

    collected_files = []
    for source in source_paths:
        src = Path(source)
        if src.is_file():
            shutil.copy2(src, output_dir / src.name)
            collected_files.append(str(output_dir / src.name))
        elif src.is_dir():
            shutil.copytree(src, output_dir / src.name, dirs_exist_ok=True)
            collected_files.append(str(output_dir / src.name))

    return {"collected_files": collected_files, "output_dir": str(output_dir)}
```

```python
) -> list[str]:
    """列出目录中匹配指定模式的文件。"""
    base = Path(directory_path)
    if recursive:
        return [str(p.relative_to(base)) for p in base.rglob(pattern) if p.is_file()]
    return [str(p.name) for p in base.glob(pattern) if p.is_file()]
```

## 五、执行流程对比

### 5.1 传统模式 vs Agent-Driven 模式

```
传统模式（ExecutionEngine + SUTDriver）：
  TaskSet → ExecutionEngine.run()
              ├── Task → HTTPDriver.invoke()
              │           ├── Jinja2 渲染模板
              │           ├── HTTP 请求发送
              │           └── 响应解析 → SUTResponse
              ├── Task → CLIDriver.invoke()
              │           ├── 构建命令行参数
              │           └── 子进程执行 → SUTResponse
              ├── ResultCollector.collect()
              └── ExecutionPackage 归档

Agent-Driven 模式（ExecutionAgent + SUT Tools）：
  TaskSet → ExecutionAgent.run_task_set()
              └── Task → ExecutionAgent.run_task()
                          ├── 构建 System Prompt + Task Prompt
                          ├── 启动 Agent Loop 会话（DeepAgents）
                          ├── Agent 理解任务，自主决策：
                          │   ├── 调用 invoke_http_sut（含 Jinja2 渲染）
                          │   ├── 或调用 invoke_cli_sut
                          │   ├── 或调用 scan_directory → collect_results
                          │   ├── 遇到错误 → 智能重试 / 降级
                          │   └── 调用 write_package 写入结果
                          └── 从 Agent 会话构建 ExecutionPackage
```

### 5.2 流程对比表

| 阶段 | 传统模式 | Agent-Driven 模式 |
|------|----------|-------------------|
| 任务理解 | 代码逻辑解析 Task 字段 | Agent 理解 Task Prompt 语义 |
| 请求构造 | Jinja2 模板变量替换 | Agent 调用 invoke_http_sut，传入模板和变量 |
| SUT 调用 | HTTPDriver/CLIDriver 固定流程 | Agent 选择并调用合适的 MCP Tool |
| 错误处理 | 预定义的重试次数和超时 | Agent 根据错误类型动态决策（重试/降级/终止） |
| 结果收集 | ResultCollector 固定逻辑 | Agent 调用 collect_results / scan_directory |
| 包归档 | ExecutionEngine 内部方法 | Agent 调用 write_package |
| 可观测性 | 日志 + ExecutionTrace | 完整 Agent 会话记录（所有决策和工具调用） |
| 扩展性 | 编写新 SUTDriver 类 | 添加新 MCP Tool 或调整 Prompt |

### 5.3 Benchmark 数据集的 Inferencer 执行路径（场景包对接）

> 对接 [13 配置管理设计](./13配置管理设计.md) §十六。对于传统 LLM benchmark 数据集（GSM8K/MMLU/HumanEval 等，`Dataset` 的 `role: test`），被测对象是模型本身而非多步 Agent，此时**不适用** Agent-Driven 的 ExecutionAgent 路径，而走更轻量的 **Inferencer 执行路径**。

两条执行路径并存，由场景包的资产类型决定：

| 路径 | 适用场景 | 驱动组件 | 输入 | 输出 |
|------|----------|----------|------|------|
| **Agent-Driven**（§三/§五.1） | 课件生成、行程规划等需要多步推理/工具调用的场景 | `ExecutionAgent` + SUT Tools | `TaskSet`（inline / `role: reference` 辅助） | `ExecutionPackage`（多文件产出） |
| **Inferencer**（本节） | benchmark 数据集（`role: test`），被测对象 = 单次模型推理 | `Inferencer` + `SUTConfig` | `Dataset(role=test)` → `TaskSet`（input/reference） | `ExecutionPackage`（prediction + reference） |

**Inferencer 执行流程**：

```
ScenarioPackage
    │
    ├── Dataset(role=test) ──► DatasetBackend.load() ──► TaskSet(input, reference)
    │
    ├── SUTConfig ────────────► Inferencer ──────────► predictions
    │                              (gen / ppl / api)
    ├── PromptTemplate ───────► formatted prompt
    │
    └── ExecutionPackage(input, prediction, reference) ──► 评估器 MetricEvaluator
```

**Inferencer 抽象**：

```python
class Inferencer(ABC):
    @abstractmethod
    def generate(self, inputs: list[str], sut_config: SUTConfig) -> list[str]: ...
```

内置实现：

- `GenInferencer`：文本生成（HuggingFace / API）。
- `PPLInferencer`：perplexity 推理（用于选择题，如 MMLU）。
- `APIInferencer`：调用远程 API（OpenAI / Claude / 自定义 gateway）。

**SUTConfig**：描述被测模型 backend、`path`、`max_out_len`、`batch_size`、`run_cfg`（如 `num_gpus`），见 [13 §十六](./13配置管理设计.md)。

**与评估引擎的衔接**：Inferencer 产出的 `ExecutionPackage` 与 Agent 路径产出的包结构一致，统一进入评估引擎；benchmark 场景使用 `MetricEvaluator`（如 `ExactMatchEvaluator`）计算指标，输出 `metrics: Record<metric_id, number>`（见 [04 §七之二](./04评估引擎设计.md)、[07 §五之二](./07评估指标与方法.md)）。

## 七、异常处理

执行引擎定义以下异常类型，覆盖 Agent-Driven 执行的各类错误场景：

```python
class ExecutionError(Exception):
    """执行引擎基础异常"""
    pass

class AgentError(ExecutionError):
    """ExecutionAgent 执行失败

    适用场景：
    - LLM Provider 调用失败（连接错误、认证失败、协议格式错误等，经 LangChain ChatModel 抛出）
    - DeepAgents / LangGraph 运行时异常（checkpointer 写入失败、图执行中断等）
    - Agent 执行超过 max_turns 限制
    - Agent 产出物解析失败
    - Agent 工具调用权限不足
    """
    pass

class AgentTimeoutError(AgentError):
    """Agent 执行超时（超过 max_turns 或 wall-clock timeout）"""
    pass

class BudgetExceededError(AgentError):
    """Agent 执行超出预算（超过 max_budget_usd）"""
    pass

class ToolExecutionError(ExecutionError):
    """MCP Tool 执行失败（HTTP 请求失败、CLI 执行错误、文件操作失败等）"""
    pass

class CollectionError(ExecutionError):
    """结果采集失败（文件复制错误、目录遍历失败等）"""
    pass

class TaskBuildError(ExecutionError):
    """任务集构建失败（模板渲染错误、LLM 生成异常等）"""
    pass
```

**Agent 错误处理策略**：

| 错误类型 | 处理策略 |
|----------|----------|
| Tool 调用失败（HTTP 超时/CLI 错误） | Agent 自主重试（最多 `max_retries` 次），或降级到其他工具 |
| 超过 max_turns | 抛出 `AgentTimeoutError`，写入包含部分结果的 ExecutionPackage |
| 超过 max_budget_usd | 抛出 `BudgetExceededError`，立即终止执行 |
| Agent 会话异常中断 | 捕获异常，记录已完成的工具调用轨迹，写入错误 ExecutionPackage |
| 工具返回意外结果 | Agent 分析错误信息，尝试修正参数后重试 |

## 七a、结构化日志

### 7a.1 设计要求

**即使使用 ExecutionAgent，系统必须输出结构化日志**。Agent 的自然语言推理过程是补充信息，不能替代机器可解析的结构化记录。

结构化日志的核心要求：

| 要求 | 说明 |
|------|------|
| **机器可解析** | 所有日志均为 JSON Lines 格式（`structlog` + JSON renderer），可被 ELK/Grafana 等工具直接消费 |
| **完整追踪链** | 每条日志包含 `run_id`、`task_id`、`trace_id`，支持全链路追踪 |
| **工具调用记录** | 每次 SUT Tool 调用生成独立日志条目，包含工具名、输入摘要、输出摘要、耗时、状态 |
| **成本可审计** | 每条日志包含 `cost_usd`、`tokens_used` 字段，支持成本归因 |
| **与评估引擎对齐** | ExecutionAgent 输出的 ExecutionPackage 结构与 PipelineEngine 评估输入要求一致 |

### 7a.2 当前实现（2026-08-21 Phase A 落地）

结构化日志与底座支撑组件已全量实现（Sprint 8 Phase A）：

| 组件 | 位置 | 说明 |

### 7a.3 完整日志模型（目标设计）

完整的结构化日志方案将包含以下数据模型和记录器：

```python
@dataclass
class AgentExecutionLog:
    """Agent 执行的结构化日志条目。"""
    # 追踪信息
    timestamp: str                     # ISO 8601
    run_id: str
    task_id: str
    trace_id: str

    event: str                         # "agent_start" | "tool_call" | "tool_result"
```
