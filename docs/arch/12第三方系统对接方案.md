# 第三方系统对接方案

> 本文档设计第三方系统（如课件制作平台）与本评测平台对接的整体方案：外部系统如何提交评估任务、平台如何自动调用评估器、结果如何回流到 Web 可观测平台、课件平台如何呈现任务状态与结果，以及面向第三方的接入文档与部署策略。
>
> 本文档属于 [01 整体架构设计](./01整体架构设计.md) 的扩展，新增"接入编排层"。复用既有能力：评估器 SDK（[04 评估引擎设计](./04评估引擎设计.md)）、可观测摄取 API 与 HMAC 认证、对象存储三态（[09 Web 可观测平台架构设计](./09Web可观测平台架构设计.md) §5/§6.3/§7/§8）。部署方案须兼容腾讯云函数（SCF），相关基础见 [09](./09Web可观测平台架构设计.md) §12.2 / §4.4。

---

## 一、背景与目标

### 1.1 现状

当前系统由两部分组成（见 [01](./01整体架构设计.md) §2.1）：

- **评估器（`evaluator/`，Python）**：开发者本地通过 `agent-eval` CLI 执行评估，产出落到 `workspace/runs/{run_id}/`，并通过 `observability` 模块（`AGENT_EVAL_*` 环境变量）把结果上传到 Web 平台。
- **Web 可观测平台（`web/`，TypeScript）**：仿 Langfuse 的多租户后端，提供摄取 API（`POST /api/public/ingest`，HMAC 鉴权）、对象存储、Query API 与前端可视化。

这条链路的前提是**"由开发者手动安装 Python 项目并执行 CLI"**。

### 1.2 问题

投入真实使用时，本系统需要与**第三方业务系统（如课件制作平台）对接**，而：

1. 课件平台**不会**在运行环境中安装评估器的 Python 项目，也**不会**手动执行 CLI——这不符合系统级集成。
2. 因此除了"开发者手动评估"路径，平台还须具备一种**被调用**的能力：第三方以系统化方式提交待评估内容，平台自动完成评估并回传结果。
3. 课件平台还需在自身界面呈现**任务状态（执行中 / 完成 / 失败）与评测结果**。

### 1.3 设计目标

| 编号 | 目标 | 验收口径 |
|------|------|----------|
| G1 | 第三方系统能以**系统化方式**提交评估任务，无需安装 Python、无需执行 CLI | 仅需 HTTP 客户端 + 平台签发的 API Key |
| G2 | 平台自动完成"接收 → 预处理 → 调用评估器 → 回传结果"全链路 | 第三方提交后零人工介入得到结果 |
| G3 | 评估任务**异步执行**，第三方可查询状态、接收回调 | 支持长耗时（LLM）评估，提交请求秒级返回 |
| G4 | 课件平台能呈现任务状态与结果 | 提供 Query API + Webhook + 可嵌入视图 |
| G5 | 部署形态兼容腾讯云函数（SCF） | Docker 先行，可平滑迁移 SCF |
| G6 | 第三方可在 Web 页面获得**详细接入文档**，简单配置即可对接 | 一个页面 + 可复制代码片段 |

### 1.4 非目标（本期不做）

- 不重写评估引擎，评估仍由 `PipelineEngine` / `eval_packages()` 承担（见 [04](./04评估引擎设计.md)）。
- 不改变 Web 平台既有的摄取契约（`/api/public/ingest` 事件 schema v1.0 不变，见 [09](./09Web可观测平台架构设计.md) §7.1）。
- 不在本期实现 Agent/MCP 自主评估模式（`agent/` 骨架属 Sprint 8+，见 [01](./01整体架构设计.md) §2.2）。
- 不做多租户计费、配额商品化。

## 二、现状 Gap 分析

在既有链路上标注第三方对接所需的环节，识别缺口：

```
第三方 ──(?)──> [预处理/打包] ──> evaluator.eval_packages() ──> observability.ResultSink ──> /api/public/ingest ──> Web
   缺口①             缺口②                  ✅ 已有                     ✅ 已有                     ✅ 已有
```

| 环节 | 现状 | 第三方对接需要 | 结论 |
|------|------|----------------|------|
| ① 接收任务 | 无（仅 CLI 入口） | HTTP 接入、鉴权、任务编排 | **缺失，需新增** |
| ② 预处理/打包 | `agent-eval pack` CLI 命令 | 可程序化调用的打包能力 | **部分缺失，需抽取** |
| 评估执行 | `eval_packages()` SDK | 同左 | ✅ 已有 |
| 结果回传 | `observability` 模块 | 同左（`AGENT_EVAL_*`） | ✅ 已有 |
| 状态/结果查询 | Web Query API（面向 Web 用户） | 面向第三方的任务态查询 + 回调 | **部分缺失，需补充** |
| 部署 | Web 有 Dockerfile；评估器未容器化 | 可独立部署、兼容 SCF | **缺失，需新增** |

**核心结论**：现成的"评估执行 + 结果回传"两环可直接复用；缺口集中在**接入编排层**——一个能接收 HTTP 任务、调度评估、维护状态、对接第三方的服务。下文称其为**评估接入服务（Evaluation Gateway，代号 `eval-gateway`）**。

## 三、整体架构

### 3.1 架构总览

新增 `eval-gateway` 作为第三方与既有能力之间的编排中间层：

```
┌─────────────────┐                                    ┌──────────────────────────┐
│  课件制作平台     │   ① 提交评估任务（HTTP + HMAC）     │   评估接入服务            │
│  / 第三方系统     │ ─────────────────────────────────> │   eval-gateway (Python)  │
│                 │   ④ 查询状态 / Webhook 回调          │   ────────────────────   │
│                 │ <─────────────────────────────────  │  • HTTP API（FastAPI）   │
│                 │                                    │  • 任务队列 + Worker      │
│                 │                                    │  • 预处理打包             │
└────────┬────────┘                                    │  • 状态机 + Webhook       │
         │                                              └───────────┬──────────────┘
         │ 嵌入 Web 视图 / Query API                                │ ② 程序化调用
         ▼                                                          ▼
┌────────────────────────────────┐                    ┌─────────────────────────────┐
│   Web 可观测平台 web/ (TS)      │ <──── ③ 结果回传 ── │   评估器 evaluator/          │
│   ──────────────────────────   │   (observability    │   eval_packages()           │
│   • /api/public/ingest (HMAC)  │    ResultSink)      │   PipelineEngine            │
│   • PG（Run/Sample/...）        │                    └─────────────────────────────┘
│   • 对象存储（MinIO/S3/COS）    │
│   • Query API / 前端可视化      │
│   • 接入文档页（新增）           │
└────────────────────────────────┘
```

数据流向（与既有链路无缝衔接）：

1. 第三方提交任务 → `eval-gateway` 鉴权、入队、返回 `job_id`。
2. Worker 取出任务 → 预处理内容 → 调用 `eval_packages()`。
3. 评估过程中 `observability.ResultSink` 把 `run/sample/constraint/artifact` 事件经 `/api/public/ingest` 回传 Web（**复用既有机制，零改动**）。
4. 第三方通过 `eval-gateway` 查询状态、接收 Webhook，或在课件平台嵌入 Web 视图。

### 3.2 关键架构决策与权衡

> **决策 D1：新增独立的 `eval-gateway` 服务（Python/FastAPI），而非在 Web（TS）后端扩展。**

| 备选方案 | 做法 | 优点 | 缺点 | 结论 |
|----------|------|------|------|------|
| **A. 独立 Python 服务**（采用） | `eval-gateway` 直接 `from agent_eval.orchestrator import eval_packages` | 与评估器同语言，零适配复用 SDK；可独立伸缩；SCF 友好 | 多一个服务与镜像 | ✅ **采用** |
| B. Web 后端扩展 | TS 新增 `/jobs` 路由，`spawn` 调 `agent-eval` CLI | 单一入口 | TS 调 Python 子进程耦合重；SCF 短连接下子进程方案受限；职责混淆 | ❌ |
| C. 第三方直连 CLI | 给第三方发 CLI + 凭据 | 无新服务 | 要求安装 Python，违背 G1；不可观测、不可控并发 | ❌ |

采用 A 的理由：评估是 Python 重计算，Web 是 TS；强行在 TS 中调度 Python 必然退化成子进程或内部 HTTP，不如直接以 Python 服务承载。`eval-gateway` 与评估器同仓同语言，`eval_packages()` 即原生 SDK 调用，无序列化损耗。

> **决策 D2：任务异步化（提交即返回 `job_id`，后台执行）。**

评估涉及 LLM 调用，单任务可能耗时数分钟至数十分钟。同步 HTTP 必然超时（SCF HTTP 触发器同步执行上限远小于此）。故**所有评估任务一律异步**：提交请求秒级返回，执行态由"查询 + Webhook"获得。这是 SCF 适配的前置条件（见 §10.2）。

> **决策 D3：复用 Web 平台的 API Key 体系做鉴权，不另起一套。**

第三方使用的 API Key 由 Web 平台统一签发与管理（[09](./09Web可观测平台架构设计.md) §6.3 已有完整签发/吊销 UI 与 HMAC 验签逻辑）。`eval-gateway` 作为 Web 的"执行伴生服务"，**只读共享 Web 的 `api_keys` 表完成验签**，实现"一把 Key 走天下"：第三方用同一把 Key 既提交任务、又能在 Web 看到结果（Key 绑定 Project，结果天然落到该 Project）。

> **决策 D4：结果回传完全复用 `observability` 模块，不新增摄取路径。**

`eval-gateway` 配置 `AGENT_EVAL_*` 环境变量后，`eval_packages()` 内部的 `ResultSink` 自动把结果推送到 Web 的 `/api/public/ingest`（[09](./09Web可观测平台架构设计.md) §8）。`eval-gateway` 不重复实现上传逻辑，只是"配好环境变量后调一次 SDK"。

> **决策 D5：`eval-gateway` 维护轻量 `jobs` 表用于执行编排，与 Web 的 `Run` 表通过 `external_run_id` 关联。**

Web 的 `Run` 是"评估运行"语义（[09](./09Web可观测平台架构设计.md) §4.1），由评估器上报。`eval-gateway` 的 `jobs` 是"第三方提交的任务"语义（含排队态、输入来源、错误堆栈、回调地址等执行编排信息）。两者 1:1，`job_id` 即 `external_run_id`。这样**职责不混淆**：Web 管可观测数据，`eval-gateway` 管任务调度。

### 3.3 在既有架构分层中的位置

参照 [01](./01整体架构设计.md) §2.1 的逻辑分层，`eval-gateway` 位于**接入层**与**编排层**之间，是"系统化接入"的补充入口（与"开发者 CLI 入口"并列）：

```
接入层：  [开发者 CLI]   [第三方 HTTP API] ◄── 新增（eval-gateway）
编排层：  Orchestrator / eval_packages() ◄── eval-gateway 复用
执行层：  PipelineEngine（既有）
评估层：  EvaluatorRegistry（既有）
数据层：  Workspace / Web PG / 对象存储（既有）
```

## 四、对接模式

### 4.1 对接模式

本期提供两种对接模式，二者配合使用：

| 模式 | 方向 | 说明 |
|------|------|------|
| **HTTP API** | 第三方 → 平台 | 第三方主动调用接口提交任务、查询状态、获取结果（G1/G2） |
| **Webhook 回调** | 平台 → 第三方 | 任务状态变更时平台主动推送通知，课件平台据此实时刷新状态（G4）；机制详见 §5.6 |

> **关于 CLI / MCP 等其他对接方式**：本期不实现（如 `agent-eval submit` 子命令、MCP Tool 等）。未来确有需求时，再单独制定相应方案，本文档不展开。

### 4.2 模式一：HTTP API（主推）

第三方持平台签发的 API Key，以 HMAC 签名调用以下接口（详见 §6）：

```
POST   /v1/jobs                 提交评估任务（异步）→ 返回 job_id
GET    /v1/jobs/{id}            查询任务状态与摘要
GET    /v1/jobs/{id}/result     获取评测结果（指标 + Web 视图链接）
POST   /v1/jobs/{id}/cancel     取消任务（尽力）
GET    /v1/health               健康检查
```

> **地址与职责边界（重要）**：
> - **统一入口**：第三方所有 API 调用（提交、查询状态、取结果、取消）都指向 `eval-gateway` **同一个地址**（如 `https://eval.example.com`），上表所有 `/v1/...` 接口共用一个 base URL、一把 API Key。
> - **查状态找 `eval-gateway`，不找 Web**：`GET /v1/jobs/{id}` 由 `eval-gateway` 处理；它维护的 `jobs` 表是任务态的权威来源。Web 只做评估数据的存储与可视化，**不作为第三方查询入口**。
> - **Web 供"人"看结果**：`https://web.example.com` 用于查看 / 嵌入评估详情（§8），第三方一般不直接调 Web API。
> - **Webhook 地址随任务提交**：第三方在 `POST /v1/jobs` 时用 `webhook_url` 字段登记回调地址，`eval-gateway` 存入 `jobs` 表，状态变更时按此地址回调（§5.6.2）。

鉴权头与 Web 摄取 API 完全一致（[09](./09Web可观测平台架构设计.md) §6.3）：

```
Authorization: Eval {publicKey}:{hmacSignature}
```

### 4.3 评估输入：支持的格式与粒度

`eval-gateway` 接收的待评估内容覆盖课件平台的两类常见形态，**两种格式、两种粒度均完整支持**。

**支持的内容格式**：

| 格式 | 说明 | 评估侧重 |
|------|------|----------|
| **HTML** | 课件网页（单页或多页） | 结构与可渲染性检查；启用视觉评估时可截图辅助判断 |
| **Markdown** | 课件文档（单文件或多文件） | 文档结构与规范检查；必要时渲染为 HTML 后再评估 |

两种格式走同一评估管线（`PipelineEngine`，见 [04](./04评估引擎设计.md)），由 format 评估器按实际格式适配，第三方无需为格式区分调用方式。

**支持的评估粒度**：

| 粒度 | 输入形态 | 打包方式 | 典型场景 |
|------|----------|----------|----------|
| **单元评估** | 一个文件夹（含多个文件，可含子文件夹） | 整个文件夹打成**一个** `ExecutionPackage`（`output/` 保留目录树） | 评估一整单元课件（多节课 / 多页） |
| **单页评估** | 单个 HTML 或 Markdown 文件 | 单文件打成**一个** `ExecutionPackage`（`output/` 仅一文件） | 评估单个课件页面 |

> 单元评估时，单元内多个文件既可整体评估、也可按模块采样，具体策略由所选 `rule_set` 决定。**无论哪种格式、哪种粒度，对第三方而言提交方式完全相同**——差别仅在于上传的是"一个文件夹"还是"一个文件"。

### 4.4 内容承载方式（第三方如何递交内容）

第三方通过以下方式把内容**提交**给 `eval-gateway`。本期仅支持**接收内容**评估，不提供平台主动拉取：

| 方式 | 字段 | 适用 | 说明 |
|------|------|------|------|
| **multipart 上传（主推）** | `file` | 通用 | 直接上传**单个文件**（单页评估）或 **zip 压缩包**（单元评估，含目录树）；`eval-gateway` 解包后打包为 `ExecutionPackage` |
| **内联 JSON** | `content` | 小体量结构化内容 | 以 JSON 直接提供产出物文本/字段，适合单页短内容 |

无论哪种方式、哪种格式、哪种粒度，`eval-gateway` 内部统一收敛为 `ExecutionPackage`（`manifest.json` + `output/`，见 [06](./06数据管理与配置规范.md)），再交给 `eval_packages()`。

## 五、`eval-gateway` 服务设计

### 5.1 服务定位与边界

| 维度 | 说明 |
|------|------|
| 语言/框架 | Python 3.11+ / FastAPI（与评估器同栈） |
| 仓库位置 | 新增 `gateway/` 子项目（与 `evaluator/`、`web/` 并列），`pyproject.toml` 依赖 `agent-eval` |
| 职责 | 接入鉴权、任务编排、预处理打包、调度评估、状态维护、回调通知 |
| **不负责** | 评估算法（委托 `eval_packages()`）、可观测存储（委托 Web）、UI 可视化（委托 Web 前端） |

### 5.2 任务模型与生命周期

任务（Job）状态机：

```
            提交                  Worker 取出              评估完成
 queued ──────────> running ─────────────────> completed
   │                   │  │
   │                   │  │ 评估异常 / 取消
   │                   │  └────> failed
   │                   │
   │ 超时/丢弃          │ 预处理失败
   └──────────────► failed
```

`jobs` 表核心字段（轻量，仅执行编排所需）：

| 字段 | 类型 | 说明 |
|------|------|------|
| `job_id` | uuid | 主键，**即 Web Run 的 `external_run_id`** |
| `project_id` / `org_id` | uuid | 来自验签所得 API Key 所属 Project（多租户隔离） |
| `status` | enum | `queued / running / completed / failed` |
| `input_kind` | enum | `upload / inline` |
| `input_ref` | text | 输入来源（上传暂存路径 / 内联内容 hash） |
| `scope` | enum | `unit / single`（单元评估 / 单页评估） |
| `rule_set_id` | text | 选用的规则集标识（默认课件规则集） |
| `run_id` | text | 评估器 `run_id`（`eval_packages()` 返回） |
| `web_run_url` | text | 指向 Web RunDetail 的链接 |
| `error` | json | 失败原因 / 堆栈摘要 |
| `webhook_url` | text | 第三方回调地址 |
| `created_at` / `started_at` / `finished_at` | timestamptz | 时间戳 |

> 与 Web `Run` 的关系：`job.status` 映射 `Run.status`（`queued/running` → `running`，`completed` → `completed`，`failed` → `failed`，见 [09](./09Web可观测平台架构设计.md) §4.1）。两者由 `ResultSink` 上报的 run 事件天然对账（`external_run_id = job_id`）。

### 5.3 异步执行架构

```
┌──────────── eval-gateway 进程/容器 ─────────────┐
│  FastAPI (HTTP) ──入队──> 任务队列 ──取出──> Worker 池
│                            │                     │
│                            │                     ├─ 预处理打包
│                            │                     ├─ eval_packages()   （同步阻塞，长耗时）
│                            │                     ├─ 状态更新 jobs/webhook
│                            └ PG (jobs 表)        └─ ResultSink 自动回传 Web
└──────────────────────────────────────────────────┘
```

- **队列实现分形态**：本地 Docker 用**进程内队列 + PG 持久化**（或 SQLite）；SCF 形态换为 **TDMQ / COS 事件触发**（见 §10.2）。队列接口抽象，切换实现不改动业务逻辑。
- **Worker 并发**：可配置并发数（默认按 CPU/LLM 限流），单 Worker 串行执行一个 Job（评估内部已有缓存与并发控制，见 [04](./04评估引擎设计.md)）。
- **失败与重试**：评估失败 → `failed` + `error`；网络瞬时失败由 `ResultSink` 离线队列兜底（[09](./09Web可观测平台架构设计.md) §8.4）。评估本身的失败不重试（结果有明确语义），但支持第三方重新提交。

### 5.4 预处理与打包（收敛为 `ExecutionPackage`）

第三方内容进入后（HTML 或 Markdown、单页或单元，见 §4.3），统一产出 `ExecutionPackage`（`manifest.json` + `output/`，见 [06](./06数据管理与配置规范.md)）：

```
内容(multipart/inline, 单页或单元) ──> 物化到临时目录 ──> PackageBuilder ──> ExecutionPackage ──> eval_packages()
```

- **格式适配**：`PackageBuilder` 按文件实际类型（`.html` / `.md` 等）记录到 manifest，评估时由 format 评估器按格式适配（[04](./04评估引擎设计.md)）；HTML 可触发截图做视觉评估。
- **粒度处理**：单页 → `output/` 仅含单文件；单元 → `output/` 保留完整目录树，单元内多文件的整体/采样策略由 `rule_set` 决定。

> **复用说明**：`PackageBuilder`（`evaluator/agent_eval/storage/builder.py:29`）已有独立类，可直接 `import` 使用，`eval-gateway` 无需再抽取。唯一需要从 `agent-eval pack` CLI（`evaluator/agent_eval/cli/main.py:36-58`）复制的辅助逻辑是 `_content_hash()`（目录稳定哈希），作为 gateway 的打包工具函数即可。

`rule_set` 来源：

- **默认**：`eval-gateway` 内置课件评估规则集（预置目录，与 [07](./07评估指标与方法.md) 指标体系一致）。
- **可选**：第三方传 `rule_set_id` 指定预置规则集；Sprint A 额外提供 `format-only` 规则集用于 CI/冒烟（无 LLM 依赖）。
- **远期**：支持上传自定义规则集。

### 5.5 结果回传（复用 `observability`，零改动）

`eval-gateway` 仅需在调用评估前设置环境变量（或等价的显式配置）：

```bash
AGENT_EVAL_HOST=https://web.example.com
AGENT_EVAL_PUBLIC_KEY=pk-eval-...
AGENT_EVAL_SECRET_KEY=sk-eval-...
AGENT_EVAL_PROJECT=<project-of-api-key>
AGENT_EVAL_UPLOAD=true
```

随后 `eval_packages()` 完成评估，gateway 需**显式调用**回传：

```python
from agent_eval.observability import load_config, ResultSink

sink = ResultSink(load_config(upload_override=True))
sink.flush(
    result,
    run_workspace=result.run_workspace.root if result.run_workspace else None,
    package_dir=package_dir,
)
```

`eval-gateway` **不重新实现**任何上传逻辑；它仅负责在评估完成后显式触发一次 `ResultSink.flush()`。

注意：便捷函数 `flush()`（`observability/sink.py:288`）**不接受 `package_dir`**，不能用于上传源文件制品；必须调用类方法 `ResultSink.flush()` 才能传 `package_dir`。

### 5.6 状态查询与 Webhook 回调

评估任务异步执行（D2）：第三方提交后立刻拿到 `job_id`，结果要等评估跑完。第三方如何得知"现在跑到哪了 / 是否完成"？提供**两种互补机制**——主动查询（拉）与回调推送（推）：

| 机制 | 方向 | 触发方 | 实时性 | 适用 |
|------|------|--------|--------|------|
| **查询（Pull）** | 第三方 → 平台 | 第三方主动调接口 | 取决于轮询间隔 | 兜底、无公网入口的系统、调试 |
| **Webhook（Push）** | 平台 → 第三方 | 状态变更时平台主动推 | 近实时（秒级） | 课件平台实时刷新状态（**推荐**） |

#### 5.6.1 主动查询（Pull）

第三方持 `job_id` 调用查询接口（契约见 §6.3 / §6.4）：

- `GET /v1/jobs/{id}` —— 任务状态 + 指标摘要；
- `GET /v1/jobs/{id}/result` —— 完整结果（仅 `completed` 后有意义）。

**轮询策略建议**：

- 提交后先用短间隔（如 5s）探测是否进入 `running`，之后放宽至 15–30s，避免无谓请求；
- 收到 `completed` / `failed` 即停止；
- 遇 429（限流）或 5xx 时指数退避；
- 即便配了 Webhook，也建议保留一个低频（如 60s）轮询作**补偿**，防止漏收回调。

```python
# 轮询伪代码
while True:
    job = GET(f"/v1/jobs/{job_id}")           # 带 HMAC 签名
    if job["status"] in ("completed", "failed"):
        break
    sleep(15)
```

#### 5.6.2 Webhook 回调（Push，推荐）

第三方在**提交任务时**通过 `webhook_url` 字段登记回调地址；任务状态发生关键变更时，`eval-gateway` 主动向该地址 `POST` 通知。

**触发的状态变更事件**：

| 事件 | 触发时机 | 载荷要点 |
|------|----------|----------|
| `job.running` | Worker 开始执行 | `status: running`、`started_at` |
| `job.completed` | 评估成功完成 | `status: completed`、`metrics_summary`、`result_url`、`web_run_url` |
| `job.failed` | 评估失败 / 取消 | `status: failed`、`error` |

> `queued` 态不触发回调——提交响应中已包含该态。载荷结构见 §6.5。

**可靠性保证**：

- **签名防伪造**：每个回调请求带 `Authorization: Eval {publicKey}:{signature}` 头（与提交请求同一套 HMAC 算法，签名串含请求体 sha256）；第三方**必须先验签再处理**，防止伪造回调篡改课件平台展示。
- **重试**：第三方对回调返回 `2xx` 表示已收到；非 `2xx` 或超时（如 10s）则 `eval-gateway` 按**指数退避**重试（如 30s / 2m / 10m / 1h，最多 N 次）。
- **幂等**：同一事件可能因重试被投递多次，载荷含 `event_id`，第三方应按 `event_id` 去重。
- **顺序**：单任务事件按 `running → completed/failed` 有序；跨任务不保证全局顺序，以载荷中的 `status` / `timestamp` 为准。

#### 5.6.3 两种机制如何配合（推荐用法）

```
                  提交(带 webhook_url)
第三方 ─────────────────────────────────> eval-gateway   返回 job_id, status=queued
  ▲                                                        │ Worker 执行评估
  │ ① Webhook: job.running   (近实时)                       │
  │ <───────────────────────────────────────────────────────│
  │                                                        │
  │ ② Webhook: job.completed (近实时, 带指标)                │
  │ <───────────────────────────────────────────────────────│
  │                                                        │
  │ ③ (兜底) 若担心漏收 → 低频轮询 GET /v1/jobs/{id}         │
  │ ───────────────────────────────────────────────────────>│
```

**推荐**：以 **Webhook 为主**（近实时、省请求），辅以**低频轮询作补偿**。课件平台据此把"评测中"刷新为"评测完成"。若第三方处于纯内网、无公网入口，无法接收 Webhook，则只能用查询轮询。

> Webhook 要求第三方有一个可被 `eval-gateway` 访问的 HTTP 端点（公网或与平台内网互通）；课件平台若不具备（如纯前端环境），退化为仅用查询轮询。两种机制的接口契约分别见 §6.3（查询）与 §6.5（Webhook）。

## 六、接口契约

### 6.1 认证

完全复用 Web 的 API Key + HMAC（[09](./09Web可观测平台架构设计.md) §6.3）：

```
Authorization: Eval {publicKey}:{signature}
signature = HMAC_SHA256(secret, "POST\n/v1/jobs\n" + sha256(body_bytes))
```

验签：`eval-gateway` 只读查询 Web 共享 PG 的 `api_keys` 表（按 `publicKey` 取 `secretEncrypted`，AES-256-GCM 解密，重算 HMAC，常量时间比较），逻辑与 Web 的 `apiKeyAuth` 中间件一致。

> **Scope 扩展**：Web 现有 API Key scope 为 `ingest`。建议新增 `eval:submit` / `eval:read` 两个 scope，平台签发 Key 时按需授予；`eval-gateway` 按接口校验 scope。最小改动下也可暂复用 `ingest` scope（提交评估本质即触发一次写入数据流）。

### 6.2 提交评估任务

```
POST /v1/jobs
Content-Type: multipart/form-data（上传）或 application/json（内联）
Authorization: Eval {publicKey}:{signature}
```

**上传示例**（单元评估传 zip；单页评估把 `file` 换成单个 `.html` / `.md` 文件即可）：

```
curl -X POST https://eval.example.com/v1/jobs \
  -H "Authorization: Eval pk-eval-xxx:$SIG" \
  -F "file=@unit-fractions.zip" \
  -F "task_title=三年级数学-分数入门(单元)" \
  -F "rule_set_id=coursework-default" \
  -F "webhook_url=https://courseware.example.com/eval/callback"
```

**内联 JSON 示例（小体量单页，Markdown）**：

```json
{
  "content": { "filename": "lesson-01.md", "text": "# 分数入门 第1节 ..." },
  "task_title": "分数入门-第1页",
  "rule_set_id": "coursework-default",
  "webhook_url": "https://courseware.example.com/eval/callback"
}
```

**响应**（`202 Accepted`）：

```json
{
  "job_id": "job_01HXY...",
  "status": "queued",
  "web_run_url": "https://web.example.com/projects/{slug}/runs/job_01HXY...",
  "poll_url": "https://eval.example.com/v1/jobs/job_01HXY..."
}
```

### 6.3 查询任务状态

```
GET /v1/jobs/{id}
```

```json
{
  "job_id": "job_01HXY...",
  "status": "completed",
  "project_id": "...",
  "created_at": "2026-06-29T03:10:00Z",
  "started_at": "2026-06-29T03:10:01Z",
  "finished_at": "2026-06-29T03:12:48Z",
  "run_id": "20260629-031001-abc",
  "metrics_summary": { "dr": 0.95, "cpr": 0.90, "avg_reward": 0.72 },
  "web_run_url": "https://web.example.com/projects/{slug}/runs/job_01HXY...",
  "error": null
}
```

`metrics_summary` 取自 Web Run 的一等指标列（`dr/cpr/avgReward/...`，[09](./09Web可观测平台架构设计.md) §4.1），由 `eval-gateway` 经 Web Query API 回查或评估结果直读。

### 6.4 获取结果

```
GET /v1/jobs/{id}/result
```

返回完整指标、失败明细（`failureBreakdown`）、样本级评分，以及指向 Web 的**制品预览 / 报告链接**。课件平台可直接嵌这些链接（见 §8.2）。

### 6.5 Webhook 回调

任务状态变更时 `eval-gateway` 主动 POST 第三方 `webhook_url`：

```json
{
  "event": "job.completed",
  "job_id": "job_01HXY...",
  "status": "completed",
  "metrics_summary": { "dr": 0.95, "cpr": 0.90 },
  "result_url": "https://eval.example.com/v1/jobs/job_01HXY.../result",
  "web_run_url": "https://web.example.com/projects/{slug}/runs/job_01HXY...",
  "timestamp": "2026-06-29T03:12:48Z"
}
```

请求带 `Authorization: Eval ...` 签名头（签名串由"请求方法、回调路径、请求体 sha256"按 §6.1 方式拼接），第三方**必须验签**后再处理，防止伪造回调篡改课件平台展示。可靠性策略（重试 / 幂等 / 顺序）见 §5.6.2。事件类型：`job.running` / `job.completed` / `job.failed`。

### 6.6 错误码

| HTTP | code | 含义 |
|------|------|------|
| 401 | `AUTH_INVALID` | 签名错误 / Key 失效 |
| 403 | `SCOPE_FORBIDDEN` | Key 无 `eval:submit` 权限 |
| 404 | `JOB_NOT_FOUND` | 任务不存在或不属于该 Key 的 Project |
| 413 | `PAYLOAD_TOO_LARGE` | 上传内容超限 |
| 422 | `INPUT_INVALID` | 内容无法解析为有效 `ExecutionPackage` |
| 429 | `RATE_LIMITED` | 触发限流（令牌桶，[09](./09Web可观测平台架构设计.md) §7.4） |

## 七、部署方案

### 7.1 Docker 化（开发 / 通用部署）

新增 `docker/gateway/Dockerfile`，与 Web 镜像同基（腾讯云 CCR），并新增 `gateway` 服务到 `docker-compose.yml`：

```yaml
# docker-compose.yml（增量）
gateway:
  build:
    context: .
    dockerfile: docker/gateway/Dockerfile
  env_file: ./.env
  environment:
    - AGENT_EVAL_HOST=http://web:9000        # 容器内回指 Web
    - AGENT_EVAL_UPLOAD=true
    - EVALGATEWAY_DATABASE_URL=...           # 共享 Web 的 PG（只读验签 + jobs 表）
    - EVALGATEWAY_QUEUE=pg                   # 本地用 PG 持久化队列
  ports:
    - "9102:9000"                            # 留出 9000 给 Web；对齐 §10.2 SCF 内部仍 9000
  depends_on: [postgres, web]
```

Dockerfile 要点（沿用项目腾讯云 CCR 基镜约定，见 [09](./09Web可观测平台架构设计.md) §12.1）：

```dockerfile
FROM ccr.ccs.tencentyun.com/sasan/python:3.11-slim
WORKDIR /app
# 评估器 + 网关同装（网关 pyproject 以路径依赖 agent-eval）
COPY evaluator ./evaluator
COPY gateway ./gateway
RUN pip install -e ./evaluator -e ./gateway
# 容器内监听端口默认 9000 —— 腾讯云函数 SCF 要求容器默认端口为 9000，生产勿改
ENV EVALGATEWAY_PORT=9000
EXPOSE 9000
CMD sh -c "uvicorn eval_gateway.main:app --host 0.0.0.0 --port ${EVALGATEWAY_PORT}"
```

本地全栈：`make docker-up` 后，第三方对接地址指向 `gateway:9102`，Web 仍 `9000`。

### 7.2 腾讯云函数（SCF）适配

> 既有 SCF 基础见 [09](./09Web可观测平台架构设计.md) §12.2（生产部署）、§4.4（serverless 连接池 PgBouncer）、§5（对象存储 COS 三态）。

SCF 是 serverless、短连接、同步触发有超时上限。结合 D2（任务必须异步），`eval-gateway` 在 SCF 形态下**拆为两个函数**：

| SCF 函数 | 触发器 | 职责 | 超时 |
|----------|--------|------|------|
| `eval-gateway-api` | API 网关（HTTP，同步） | 接收任务、入队、查状态、取结果、Webhook；**秒级响应** | 短（如 30s） |
| `eval-gateway-worker` | 异步执行 / 消息队列（TDMQ）/ COS 事件 | 消费任务 → 预处理 → `eval_packages()` → 回传 | 长（异步执行最长 24h） |

适配要点：

1. **状态外置**：`jobs` 表与 Web 共享同一云 PG（CDB），经 PgBouncer 连接池（[09](./09Web可观测平台架构设计.md) §4.4）应对 SCF 短连接。两个函数通过 PG 解耦，无需常驻进程间通信。
2. **队列外置**：`api` 函数将任务写入 **TDMQ**（腾讯云消息队列）或落 COS 触发事件；`worker` 函数被异步唤醒消费。本地 Docker 的进程内/PG 队列在 SCF 形态无缝替换为 TDMQ（队列接口已抽象，见 §5.3）。
3. **端口约定**：API 函数仍监听 `9000`（对齐 SCF 默认，见 [09](./09Web可观测平台架构设计.md) §12.2）。
4. **对象存储与大文件**：制品经 `ResultSink` 走 COS presigned（[09](./09Web可观测平台架构设计.md) §5.3）；SCF 对单次请求体大小有上限，超大单元 zip 上传在 SCF 形态下需通过分块上传或平台侧对象存储中转（具体方案待 Sprint C 定）。
5. **冷启动**：`worker` 依赖评估器与 LLM 客户端，镜像需预热/精简；评估器已离线优先（[01](./01整体架构设计.md) §1.1），冷启动影响可控。
6. **健康检查**：`GET /v1/health` 供 SCF 探活（[09](./09Web可观测平台架构设计.md) §12.4）。

> 注：本期优先交付 Docker 形态跑通全链路；SCF 拆分作为部署演进（见 §13 Sprint C），因队列/连接池基础设施已在 [09](./09Web可观测平台架构设计.md) 铺设，迁移成本主要在 SCF 配置与镜像瘦身。

### 7.3 配置管理

`eval-gateway` 配置统一走环境变量（与项目约定一致，见 [09](./09Web可观测平台架构设计.md) §12.3），纳入 `.env.example`：

```
# eval-gateway
EVALGATEWAY_DATABASE_URL=postgresql://...        # 共享 Web PG
EVALGATEWAY_QUEUE=pg|tdmq                         # 队列后端
EVALGATEWAY_WORKER_CONCURRENCY=2
EVALGATEWAY_MAX_UPLOAD_MB=50
EVALGATEWAY_PORT=9000                           # 容器监听端口（SCF 要求 9000，默认勿改）
EVALGATEWAY_WEB_BASE_URL=https://web.example.com  # 生成 web_run_url
# 评估器回传（透传给 observability，见 §5.5）
AGENT_EVAL_HOST / AGENT_EVAL_PUBLIC_KEY / AGENT_EVAL_SECRET_KEY / AGENT_EVAL_UPLOAD
```

> **服务级凭据**：`AGENT_EVAL_*` 是 `eval-gateway` 作为"统一上报身份"调用 Web 摄取的凭据。两种取法：
> (a) **服务级固定凭据**：`eval-gateway` 用一把平台级 Key 上报，所有任务结果落到对应 Project 由任务参数指定——简单、利于 SCF；
> (b) **透传第三方凭据**：用第三方提交时那把 Key 上报——结果天然归属第三方 Project，更细粒度。
> 推荐 (a) 起步（SCF 友好、凭据集中），按需演进到 (b)。安全红线遵守项目约定：密钥严禁入库，走 `.env` / SCF 环境变量。

页面静态渲染，内容来自一份可维护的 Markdown / 配置，避免硬编码到组件。

### 9.2 文档内容大纲

1. **概述**：对接流程一张图（提交 → 状态 → 结果）。
2. **准备**：在平台创建 Project → 签发 API Key（链接到 Key 管理面板，[09](./09Web可观测平台架构设计.md) §6.3）。
3. **鉴权**：HMAC 签名算法 + 各语言签名示例（Python / Node / curl）。
4. **提交任务**：`POST /v1/jobs` 示例（单元/单页、上传/内联）+ 字段表 + 支持格式（HTML / Markdown）。
5. **获取结果**：查询接口 + Webhook 配置说明。
6. **状态码 / 错误码**：表（§6.6）。
7. **课件平台集成示例**：状态流转 + 嵌入视图/拉取结果的最小代码。
8. **代码片段库**：可复制的 curl / Python SDK / TypeScript 片段（与现有"接入代码片段"风格一致，见 [09](./09Web可观测平台架构设计.md) §十）。
9. **限额与约束**：上传上限、并发、保留期（[09](./09Web可观测平台架构设计.md) §12.5）。

### 9.3 SDK（可选，提升体验）

提供薄封装客户端（`pip install agent-eval-gateway` / npm 包），内部仅是 HTTP + HMAC 签名，降低第三方接入成本。可作为 Sprint B 增量。

## 十、安全

| 项 | 措施 |
|----|------|
| 鉴权 | 复用 HMAC + API Key（[09](./09Web可观测平台架构设计.md) §6.3）；Webhook 回调带签名，第三方可验签防伪造 |
| 多租户隔离 | `eval-gateway` 所有读写按验签所得 `project_id/org_id` 过滤；越权返回 404（不泄露存在性，与 Web `tenantGuard` 一致，[09](./09Web可观测平台架构设计.md) §6.4） |
| 上传安全 | zip 解包限制解压总大小与文件数、路径穿越（zip-slip）防护；限制允许的文件类型（HTML / Markdown 及其静态资源） |
| 凭据 | 服务级凭据走 `.env` / SCF 环境变量；严禁入库（遵守 CLAUDE.md 安全红线） |
| 限流 | 复用令牌桶（按 API Key，[09](./09Web可观测平台架构设计.md) §7.4） |
| 审计 | 关键动作（提交/取消）写入 Web `AuditLog`（[09](./09Web可观测平台架构设计.md) §6.5） |
| LLM 凭据 | 评估所需 LLM Key 由 `eval-gateway` 侧持有，不暴露给第三方 |

## 十二、风险与权衡

| 风险 | 影响 | 缓解 |
|------|------|------|
| 评估长耗时 vs SCF 超时 | 任务超时失败 | D2 异步 + worker 长超时；本地 Docker 先行（§7.1） |
| 共享 Web PG 做验签 | 耦合 DB schema | 只读 `api_keys` 单表；schema 变更属 [09](./09Web可观测平台架构设计.md) 既有治理范围 |
| 第三方内容体积/安全 | 解压炸弹（超大 zip / 海量小文件） | 上传限额 + 解压大小/数量上限 + zip-slip 防护（§10） |
| `PackageBuilder` 抽取改动评估器 | 影响 CLI | 纯重构，CLI 与网关共用同一函数；配单元测试（`tmp_path` 隔离） |
| 服务级 vs 透传凭据 | 结果归属粒度 | (a) 起步、(b) 演进（§7.3） |
| 冷启动（SCF worker） | 首次任务慢 | 镜像精简；评估器离线优先（[01](./01整体架构设计.md) §1.1） |
