# 第三方系统对接方案

> 本文档设计第三方系统（如课件制作平台）与本评测平台对接的整体方案：外部系统如何提交评估任务、平台如何自动调用评估器、结果如何回流到 Web 可观测平台、课件平台如何呈现任务状态与结果，以及面向第三方的接入文档与部署策略。
>
> 本文档属于 [01 整体架构设计](./01整体架构设计.md) 的扩展。执行细节与数据模型参见 [09 Web 可观测平台架构设计](./09Web可观测平台架构设计.md) §7.7，部署运维参见 [09](./09Web可观测平台架构设计.md) §十二。

---

## 一、背景与目标

### 1.1 现状

当前系统由三部分组成（见 [01](./01整体架构设计.md) §2.2 / §3.1）：

- **评估器（`evaluator/`，Python）**：开发者本地通过 `agent-eval` CLI 执行评估，产出落到 `workspace/runs/{run_id}/`，并通过 `observability` 模块（`AGENT_EVAL_*` 环境变量）把结果上传到 Web 平台。
- **Web 可观测平台（`web/`，TypeScript）**：仿 Langfuse 的多租户后端，提供摄取 API（`POST /api/public/ingest`，Bearer API Key 鉴权）、对象存储、Query API 与前端可视化。**第三方任务提交入口（`POST /api/v1/jobs`）已合并至 Web 后端**。
- **executor（`executor/`，Python）**：从原 `eval-gateway` 拆分出的评测执行器，部署为腾讯云 SCF 事件函数（Job 镜像 + 异步执行，最长 24h），或本地 worker 模式轮询 `public.eval_jobs`。

### 1.2 问题

投入真实使用时，本系统需要与**第三方业务系统（如课件制作平台）对接**，而：

1. 课件平台**不会**在运行环境中安装评估器的 Python 项目，也**不会**手动执行 CLI——这不符合系统级集成。
2. 因此除了"开发者手动评估"路径，平台还须具备一种**被调用**的能力：第三方以系统化方式提交待评估内容，平台自动完成评估并回传结果。
3. 课件平台还需在自身界面呈现**任务状态（执行中 / 完成 / 失败）与评测结果**。

### 1.3 设计目标

| 编号 | 目标 | 验收口径 |
|------|------|----------|
| G1 | 第三方系统能以**系统化方式**提交评估任务，无需安装 Python、无需执行 CLI | 仅需 HTTP 客户端 + 平台签发的 API Key |
| G2 | 平台自动完成"接收 → 预处理 → 调用评估器 → 回传结果"全链路 | 第三方提交后零人工介入得到结果 |
| G3 | 评估任务**异步执行**，第三方可查询状态、接收回调 | 支持长耗时（LLM）评估，提交请求秒级返回 |
| G4 | 课件平台能呈现任务状态与结果 | 提供 Query API + Webhook（规划中）+ 可嵌入视图 |
| G5 | 部署形态兼容腾讯云函数（SCF） | Docker 先行，生产 executor 部署为 SCF 事件函数 |
| G6 | 第三方可在 Web 页面获得**详细接入文档**，简单配置即可对接 | 一个页面 + 可复制代码片段 |
| G7 | 项目可设为**公开**，公开后评测详情页可被第三方 iframe 直接嵌入，终端用户免登录 | 项目公开开关 + 直接用 `web_run_url` 嵌入 |
| G8 | 提供**评测速览** API：一眼看过没过 / 多少分 + 各评测项得分与失败原因 | 单个速览端点；深度详情走 iframe |

### 1.4 非目标（本期不做）

- 不重写评估引擎，评估仍由 `PipelineEngine` / `eval_packages()` 承担（见 [04](./04评估引擎设计.md)）。
- 不改变 Web 平台既有的摄取契约（`/api/public/ingest` 事件 schema v1.0 不变，见 [09](./09Web可观测平台架构设计.md) §7.1）。
- Webhook 回调已规划但**本期未实现**，当前以轮询 `GET /api/v1/jobs/{id}` 为准。
- 不做多租户计费、配额商品化。

## 二、整体架构

### 2.1 架构总览

第三方对接入口已**合并进 Web 后端**，评估执行由独立 `executor` 承担：

```
┌─────────────────┐                                    ┌──────────────────────────┐
│  课件制作平台     │   ① 提交评估任务（HTTP + Bearer）   │   Web 可观测平台后端      │
│  / 第三方系统     │ ─────────────────────────────────> │   Express (TypeScript)   │
│                 │   ④ 查询状态 / 嵌入 Web 视图         │   ────────────────────   │
│                 │ <─────────────────────────────────  │  · JWT 登录 / 多租户      │
│                 │                                    │  · /api/v1/jobs（提交/查询）│
│                 │                                    │  · /api/v1/rule-sets      │
│                 │                                    │  · 输入物化 / 对象存储     │
│                 │                                    │  · SCF Invoke 触发 executor│
└────────┬────────┘                                    │  · Ingestion API（Bearer） │
         │                                              └───────────┬──────────────┘
         │ 嵌入 Web 视图 / Query API                                │ ② 触发 / 轮询
         ▼                                                          ▼
┌────────────────────────────────┐                    ┌─────────────────────────────┐
│   Web 可观测平台 web/ (TS)      │ <──── ③ 结果回传 ── │   executor（Python）         │
│   ──────────────────────────   │   (per-job Bearer    │   SCF 事件函数 / worker      │
│   · /api/public/ingest (Bearer)  │    ResultSink)       │   eval_packages()           │
│   · PG（Run/Sample/...）        │                    │   按提交者身份回传           │
│   · 对象存储（MinIO/S3/COS）    │                    └─────────────────────────────┘
│   · Query API / 前端可视化      │
│   · 接入文档页（新增）           │
└────────────────────────────────┘
```

数据流向：

1. 第三方提交任务 → Web 后端 `/api/v1/jobs` 鉴权、物化输入、上传对象存储、写入 `public.eval_jobs`、触发 executor。
2. executor 下载输入 → `eval_packages()` → 按提交者身份经 `ResultSink` 回传 Web。
3. 第三方通过 `/api/v1/jobs/{id}` 查询状态、读取指标，或在课件平台嵌入 Web 视图。

### 2.2 关键架构决策与权衡

> **决策 D1：将第三方提交入口合并至 Web 后端，而非保留独立 `eval-gateway` 服务。**

| 备选方案 | 做法 | 优点 | 缺点 | 结论 |
|----------|------|------|------|------|
| **A. 合并至 Web 后端**（采用） | Web 后端新增 `/api/v1/jobs`，executor 负责执行 | 单一入口、单一鉴权体系、减少服务数量；SCF 事件函数解决长超时 | Web 后端需做输入物化与 SCF Invoke | ✅ **采用** |
| B. 保留独立 Python gateway | 独立 `eval-gateway` 服务同时做 HTTP + Worker | 与评估器同语言 | 多一个服务与镜像；HTTP 函数仍需 900s 限制 | ❌（已推翻） |
| C. 第三方直连 CLI | 给第三方发 CLI + 凭据 | 无新服务 | 要求安装 Python，违背 G1；不可观测、不可控并发 | ❌ |

采用 A 的理由：原 `eval-gateway` 的 Web API 与 Worker 职责天然解耦——Web 后端更适合做接入层（同 Express 生态、同数据库连接），而执行侧独立为 SCF 事件函数后可突破 900s 限制。

> **决策 D2：评测执行拆分为独立 `executor`，部署为 SCF 事件函数（Job 镜像 + 异步执行）。**

- Web 后端接收任务后**立即返回** `job_id`（202 Accepted），不等待评估完成。
- 生产通过腾讯云 SCF `Invoke`（`InvocationType=Event`）异步触发 executor；executor 每次只执行一个 job，执行完即退出。
- 本地开发用 `executor` worker 模式轮询 `public.eval_jobs`，无需真实 SCF。

> **决策 D3：复用 Web 平台的 API Key 体系做鉴权，不另起一套。**

第三方使用的 API Key 由 Web 平台统一签发与管理（[09](./09Web可观测平台架构设计.md) §6.3）。`/api/v1/jobs` 与 `/api/public/ingest` 共用同一 `api_keys` 表，实现"一把 Key 走天下"：第三方用同一把 Key 既提交任务、又能在 Web 看到结果（Key 绑定 Project，结果天然落到该 Project）。

> **决策 D4：结果回传完全复用 `observability` 模块，按提交者身份 per-job 回传。**

executor 按 `job.api_key_id` 解密提交者 token，构造 per-job `ResultSink` 配置，把结果推到 Web 的 `/api/public/ingest`。这样第三方结果落到**第三方自己的 Project**，而非 gateway 服务级固定 Project。

> **决策 D5：任务表由 Web 统一 owning，executor 只读写 `public.eval_jobs`。**

`public.eval_jobs` 由 Prisma 治理，与原 Web 数据模型统一迁移。executor 通过 SQLAlchemy/asyncpg 读写同一表，不持有独立 schema。

## 三、对接模式

### 3.1 本期提供模式

| 模式 | 方向 | 说明 |
|------|------|------|
| **HTTP API（提交 + 速览）** | 第三方 → 平台 | 提交任务、轮询状态；调**速览**接口看"过没过 / 多少分 + 各评测项失败原因"（G1/G2/G3/G8） |
| **MCP 接入** | 第三方（智能体） → 平台 | 任意 MCP 兼容客户端（Claude Code / Cursor / Windsurf 等）经 MCP 工具提交/查询/速览，**同一把 API Key、同一功能**（§3.7） |
| **嵌入 Web 视图** | 平台 → 第三方（人眼看） | 项目设为**公开**后，iframe 直接嵌入运行/样本详情页，免登录（G7） |

> **关于 Webhook 回调**：已规划（`job.running` / `job.completed` / `job.failed`），**本期未实现**。当前请以轮询 `GET /api/v1/jobs/{id}` 为准。

### 3.2 模式一：HTTP API（主推）

第三方持平台签发的 API Key，以 **Bearer** 方式调用以下接口：

```
POST   /api/v1/jobs                  提交评估任务（异步）→ 返回 job_id
GET    /api/v1/jobs/{id}             查询任务状态与指标
GET    /api/v1/jobs/{id}/overview    评测速览：过没过 / 分数 + 各评测项得分与失败原因
GET    /api/v1/rule-sets             规则集目录（含所需能力）
GET    /api/v1/health                健康检查
```

> **一把 Key 走天下**：上述接口统一用项目 API Key（Bearer）即可，不再细分 scope。深度详情（逐条约束 / 制品预览）不开放 API，由第三方 iframe 嵌入公开页面查看（见 §3.5）。

> **统一入口**：第三方所有 API 调用都指向 **Web 后端地址**（如 `https://eval.bj33smarter.com`），上表所有 `/api/v1/...` 接口共用一个 base URL、一把 API Key。
>
> **鉴权**：`Authorization: Bearer {api_key}`，无需计算签名。

### 3.3 评估输入：支持的格式与粒度

`POST /api/v1/jobs` 接收的待评估内容覆盖课件平台的两类常见形态，**两种格式、两种粒度均完整支持**。

**支持的内容格式**：

| 格式 | 说明 | 评估侧重 |
|------|------|----------|
| **HTML** | 课件网页（单页或多页） | 结构与可渲染性检查；启用视觉评估时可截图辅助判断 |
| **Markdown** | 课件文档（单文件或多文件） | 文档结构与规范检查；必要时渲染为 HTML 后再评估 |

两种格式走同一评估管线（`PipelineEngine`，见 [04](./04评估引擎设计.md)），由 format 评估器按实际格式适配，第三方无需为格式区分调用方式。

**支持的评估粒度**：

| 粒度 | 输入形态 | 打包方式 | 典型场景 |
|------|----------|----------|----------|
| **单元评估** | 一个文件夹（含多个文件，可含子文件夹） | 整个文件夹打成**一个** `ExecutionPackage`（`output/` 保留目录树） | 评估一整单元课件（多节课 / 多页） |
| **单页评估** | 单个 HTML 或 Markdown 文件 | 单文件打成**一个** `ExecutionPackage`（`output/` 仅一文件） | 评估单个课件页面 |

> 单元评估时，单元内多个文件既可整体评估、也可按模块采样，具体策略由所选 `rule_set` 决定。**无论哪种格式、哪种粒度，对第三方而言提交方式完全相同**——差别仅在于上传的是"一个 zip 压缩包"还是"一个文件"。

### 3.4 内容承载方式（第三方如何递交内容）

第三方通过以下方式把内容**提交**给 `/api/v1/jobs`。本期仅支持**接收内容**评估，不提供平台主动拉取：

| 方式 | Content-Type | 字段 | 适用 | 说明 |
|------|--------------|------|------|------|
| **上传原始字节（主推）** | `application/octet-stream` | 请求体为文件原始字节；元数据通过查询串传递：`filename`、`rule_set_id`、`task_id`、`task_title`、`task_subject` | 通用 | 直接上传**单个文件**（单页评估）或 **zip 压缩包**（单元评估，含目录树）；Web 后端做 zip 探测/解压/scope 推导 |
| **内联 JSON** | `application/json` | `{ "content": { "filename": "...", "text": "..." }, "rule_set_id": "...", ... }` | 小体量结构化内容 | 以 JSON 直接提供产出物文本/字段，适合单页短内容 |

无论哪种方式、哪种格式、哪种粒度，Web 后端内部统一收敛为 `ExecutionPackage`（`manifest.json` + `output/`，见 [06](./06数据管理与配置规范.md)），再交给 executor 执行 `eval_packages()`。

### 3.5 嵌入 Web 视图（项目公开 + iframe）

第三方系统可在自身界面用 `<iframe>` 嵌入评测详情页（运行详情 / 样本详情），终端用户**无需登录本平台**。

**方案：项目公开开关**。项目 owner 在项目设置里把项目标为**公开**（`Project.isPublic=true`，见 [09](./09Web可观测平台架构设计.md) §四，需 Prisma 迁移）。公开项目的运行/样本详情页及其 Query API **免登录可读**；第三方直接把 `web_run_url` 放进 `<iframe src>` 即可，无需任何令牌或后端换签。

```
课件平台前端(浏览器)                     评测平台
    │  <iframe src="https://eval.../run/{run_id}">
    │ ─────────────────────────────────────────>│ ① 前端守卫查 run 所属 project.isPublic
    │                                          │    公开 → 匿名模式渲染(不走 RequireAuth)
    │                                          │ ② 页面同源调 Query API(公开项目免 JWT)
    │ <──────────────── 运行/样本详情 ───────────│ ③ 制品预览按原机制(image 直链 / raw 代理)
```

**实现要点（最小改动）**：

- **数据**：`Project` 新增 `isPublic Boolean @default(false)`；owner 在项目设置页切换。
- **后端**：运行/样本详情与制品端点（`GET /api/v1/runs/:id`、`/runs/:id/samples/:sid`、`/artifacts/:id*`）改为**可选鉴权**——无 JWT 时，若所请求资源所属项目 `isPublic=true` 则放行（合成只读公开 tenant），否则维持 401/重定向登录。**写操作不受影响，仍需登录。**
- **前端**：`/run/:id`、`/run/:id/sample/:sid` 守卫在无 session 时先查"该项目是否公开"，公开则进入**匿名外壳**（无组织切换器/用户菜单/删除按钮，只读），否则跳登录。
- **iframe 防护**：对这些页面放开 `frame-ancestors`（允许第三方嵌入）；其余页面保持 `SAMEORIGIN`。

**取舍（务必告知 owner）**：

- 公开 = **任何拿到链接的人都能查看**该项目下所有运行/样本（URL 含不可猜测的 UUID，但非秘密）。仅**只读**，不暴露任何写操作或 Key。
- 由 owner 显式开启；不公开的项目行为完全不变（仍需登录）。

> **决策 D6：用"项目公开开关 + 免登录直访"，而非 Embed Token。**
> Token 方案（短期令牌 + 后端换签 + `/embed/*` 路由）对"课件平台只想嵌个详情页"的场景过重。公开开关把鉴权成本降到零：owner 一键开启，第三方 `<iframe src={web_run_url}>` 直接嵌入。代价是粒度变粗（公开是项目级、非单次链接级）——可接受，因为评测详情本就是面向协作的只读内容。沿用制品预览的"公开只读"思路（[09](./09Web可观测平台架构设计.md) §5.4）。

### 3.6 评测速览（overview）

第三方后端只需要一个答案：**过没过、多少分、各项为什么没过**。深度详情（逐条约束 reason / 制品预览）由 iframe 嵌入公开页面查看，**不再开放结构化详情 API**，避免维护两套只读口径。

当前 `GET /api/v1/jobs/{id}` 只回传顶层 `metrics` 与任务级 `error`，**不含"各项为什么没过"**。为此新增**单个**速览端点 `GET /api/v1/jobs/{id}/overview`（见 §6.6），一次返回：

- 运行级判定：`verdict`（pass/fail）+ 综合分 + 指标 + 各维度通过情况；
- 各评测项（样本）：每项的 `score` + `passed` + **失败原因**（该项未通过约束的 `name` + `reason`，聚合）。

> **决策 D7：详情只给"速览"，不给"全量结构化 API"。**
> 速览覆盖 90% 的"知道结果 + 知道原因"诉求；剩下要逐条看约束/制品的，走 iframe 复用 Web 全套可视化。少维护一组 job 维度的 run/sample 详情端点与口径，避免与 Query API 漂移。

### 3.7 模式三：MCP 接入（智能体）

任意 **MCP 兼容客户端**（Claude Code / Cursor / Windsurf / VS Code Copilot / Claude Desktop / 自研 Agent）经 MCP 协议提交评测、查询状态、看速览。**与 HTTP 同一把 API Key、同一套功能、同一租户隔离**——MCP 只是同一接入层的新 transport。

#### 3.7.1 行业调研与选型

| 议题 | 行业共识 | 本方案选择 |
|------|----------|-----------|
| 大二进制文件 | base64 仅小文件（~175KB 起损坏、~20MB 失败、膨胀上下文）；**大文件事实标准 = presigned URL + 对象存储**（MCP 只传 URL，客户端直传 S3/COS） | 大文件走 **presigned PUT**（复用本平台既有 `objectStorage.presignPut`，加 `request_input_upload` 工具）；小文件才 inline/base64 |
| 服务端框架 | 官方 `@modelcontextprotocol/sdk`（TS，MCP 母语 SDK）；FastMCP 最火但**仅 Python** | 后端为 TS/Express → **官方 TS SDK** |
| 传输 | 远程服务用 **Streamable HTTP**；stdio 仅本地子进程 | 远程第三方接入 → **Streamable HTTP**（`StreamableHTTPServerTransport`） |
| 消费端生态 | 写一次服务端，Claude Code/Cursor 等所有 MCP 客户端即插即用（远程 HTTP + header 传凭据） | 标准 MCP 服务端，客户端经 `url + headers:{Authorization:Bearer …}` 接入 |

> 决策 D8：MCP 作为 Express **同进程**的新 transport（`app.use("/api/v1/mcp", requireApiKey, mcpRouter)`），复用 `requireApiKey` 注入 `req.tenant` + `createEvalJobService(tenant)`，而非独立进程/独立 Key。理由：沿用 D1（入口合并进 Web 后端）、D3（一把 Key 走天下）；评测执行早已异步外置到 executor，接入层无长耗时阻塞，同进程零新增部署成本。

#### 3.7.2 架构与挂载

```
智能体(Claude Code/Cursor/…)
   │  MCP over Streamable HTTP + header Authorization: Bearer eval-…
   ▼
Web 后端 Express  app.use("/api/v1/mcp", requireApiKey, mcpRouter)
   │  requireApiKey → req.tenant（同一把 Key、同 scope 校验）
   ▼
McpServer(官方 TS SDK)  tools → 复用 createEvalJobService(tenant).submit/get/overview
   │                                         + readRuleSetsCatalog() / objectStorage.presignPut
   ▼
（与 HTTP 同链路）物化 → 写 eval_jobs → 触发 executor → 结果落库
```

- 路由 `/api/v1/mcp`：`/api` 前缀避开 server.ts 的前端 SPA 兜底；`requireApiKey` 前置注入 tenant，再经 MCP 请求上下文透传进各 tool handler。
- 同进程随 `node dist/server.js`，无新端口/镜像/Dockerfile；本地随 `npm run dev` 热更。生产单实例 OK（session 内存）；多实例远期需 session 亲和。
- 依赖：`web/backend/package.json` 新增 `@modelcontextprotocol/sdk`。

#### 3.7.3 工具集（与 HTTP 功能一致）

| MCP Tool | 对应 HTTP | 入参 | 出参 | 复用实现 |
|---|---|---|---|---|
| `submit_eval_job` | POST /api/v1/jobs | 见 §3.7.4（inline / base64 / object_key 分层） | `{job_id, status:"queued", project_id, poll_url, scf_request_id?}` | `evalJobService.submit` |
| `get_eval_job` | GET /api/v1/jobs/:id | `{job_id}` | `JobDto`（snake_case，内部字段不外泄） | `evalJobService.get` |
| `get_eval_job_overview` | GET /api/v1/jobs/:id/overview | `{job_id}` | `OverviewResult`（verdict/score/items[].failures[].top_issues） | `evalJobService.overview` |
| `list_rule_sets` | GET /api/v1/rule-sets | 无 | `{rule_sets:[…]}` | `readRuleSetsCatalog()` |
| `list_packages` | （HTTP 无；MCP 场景包发现专用） | 无 | `{packages:[{package_ref, scenario, package_id, version, labels, name?, description?, artifact_types[]}]}` | `buildPackagesCatalog()`（`scenarioPackage` 表） |
| `eval_health` | GET /api/v1/health | 无 | `{status:"ok", subsystem:"eval"}` | 内联 |
| `request_input_upload` | （HTTP 无；MCP 大文件专用） | `{filename, content_type?}` | `{upload_url, object_key, expires_at}` | `objectStorage.presignPut`（复用制品两段式上传基建） |

#### 3.7.4 submit 入参分层（按行业最佳实践）

MCP 工具入参为 JSON，对大二进制不友好，故 submit 按文件大小分层，三种互斥择一：

| 形态 | 字段 | 适用 | 处理 |
|------|------|------|------|
| **inline 文本** | `content:{filename, text}` | 小体量文本 | `materializeInline`（scope=single） |
| **base64 小二进制** | `file:{filename, base64}` | 中小二进制（解码后 ≤8MB） | `materializeUpload`（zip 探测→unit/single）；超 8MB 报错引导走 presigned |
| **presigned 大文件** | `input_object_key: string` | 大文件 / zip 单元 | 客户端先调 `request_input_upload` 拿 presigned PUT 直传对象存储，再把 `object_key` 传 submit；submit 校验对象存在（HEAD）后作为 job 输入，沿用 executor 经 presigned GET 下载链路 |

其余字段：`package_ref`（**必填**——executor 缺失即拒绝；格式 `scenario/package[:version_or_label]`，如 `courseware/courseware:latest` / `code/code`，可用值先调 `list_packages`；它**不是**上传返回的 `object_key`，二者无关）、`rule_set_id?`（缺省时 executor 取包内唯一规则集，包内不唯一则必填）、`task_id/task_title/task_subject?`。物化与 scope 推导不可跳过（service 内部已调 `materializeUpload/Inline`）。

#### 3.7.5 鉴权、错误、限流

- **鉴权 = 同一把 Key**：`requireApiKey` 解析 `eval-…` Bearer → sha256 查 `api_keys` → 校验未吊销/未过期/scope 含 `ingest` → 注入 `req.tenant={kind:apikey, apiKeyId, projectId, orgId, scopes}`。项目归属由 Key 决定，租户隔离与 HTTP 完全一致。
- **错误模型**：service 抛 `PlatformError{status, code}`；tool handler 捕获 → 转 **MCP 错误响应**（`isError:true` + `{code, message}`），**不依赖** Express `errorHandler`（transport 接管响应）。错误码与 HTTP 一致（`AUTH_INVALID`/`INPUT_INVALID`/`JOB_NOT_FOUND`/`PAYLOAD_TOO_LARGE`），不泄露存在性。
- **限流**：MCP 路由同挂 `rateLimiter()`（按 `apiKeyId` 令牌桶），与 HTTP 同口径。

#### 3.7.6 客户端接入（即插即用）

服务端建成后，任意 MCP 兼容客户端远程接入（示例配置）：

```jsonc
// Claude Code / Cursor / Windsurf 等：远程 MCP server
{
  "mcpServers": {
    "evalscope": {
      "url": "https://eval.bj33smarter.com/api/v1/mcp",
      "headers": { "Authorization": "Bearer eval-…" }
    }
  }
}
```

接入后客户端可调用上述 7 个工具：`list_packages` 查可用场景包及其 `package_ref` → 列规则集 → 提交评测（submit 必填 `package_ref`；小文件 inline/base64，大文件先 `request_input_upload` 直传再 submit）→ 轮询 `get_eval_job` → `get_eval_job_overview` 看过没过/各项失败原因。

#### 3.7.7 配置与安全

- **无新 env**（鉴权复用 API Key 体系）；可选 `PLATFORM_MCP_ENABLED`（bool，默认开）做开关。
- **安全**：同一把 Key + tenant 强制过滤（projectId/orgId）；presigned PUT 短时效（≤15min）+ 前缀含 project_id；base64 解码大小校验；MCP 错误不泄露存在性。

> 本节为设计（v4.0）；MCP 服务端代码实现（加依赖 + `routes/eval/mcp.ts` + server.ts 挂载 + 单测）另起任务。

## 四、任务模型与生命周期

### 4.1 任务状态机

```
            提交                  executor 领取              评估完成
 queued ──────────> running ─────────────────────> completed
   │                   │  │
   │                   │  │ 评估异常 / 取消
   │                   │  └────> failed
   │                   │
   │ 预处理失败          │ 运行中崩溃（mark_failed 前）
   └──────────────► failed
```

### 4.2 `public.eval_jobs` 核心字段

`public.eval_jobs` 由 Web 后端写入（`queued`），executor 更新状态机（`running` → `completed`/`failed`）。核心字段见 [09 Web 可观测平台架构设计](./09Web可观测平台架构设计.md) §4.1。

与 Web `Run` 的关系：`job.id` 即 Web `Run.external_run_id`。两者由 `ResultSink` 上报的 run 事件天然对账。

## 五、执行架构

### 5.1 本地开发

```
Web 后端 ──写入──> public.eval_jobs (queued)
                         ▲
                         │ 轮询
                  executor (worker 模式)
```

- `TENCENT_SCF_ENABLED=false`。
- `executor` 容器以 worker 模式运行，按配置间隔轮询 `public.eval_jobs`。
- 领取任务后流程与生产 SCF 模式一致。

### 5.2 生产（SCF 事件函数）

```
Web 后端 ──SCF Invoke(Event)──> agent-eval-executor (SCF 事件函数 + Job 镜像 + 异步执行)
                                     │
                                     ▼
                          读 SCF_CUSTOM_CONTAINER_EVENT
                          经 presigned URL 下载输入
                          eval_packages()
                          per-job ResultSink.flush
                                     │
                                     ▼
                          Web /api/public/ingest + /api/public/artifacts/url
```

**SCF 函数侧硬性要求**（控制台 / Terraform 创建）：

- 必须为「**事件函数 + Job 镜像**」。
- 创建时勾选「**异步执行**」（创建后锁死、不可修改，只能重建函数）。
- `timeout = 86400`。
- 镜像为 `agent-eval-executor`。

### 5.3 失败兜底

采用**乐观模型**：

- executor 启动后**第一时间** `mark_running`，缩小「已触发但状态仍 queued」的窗口。
- 评估过程任意异常都走 `mark_failed`，不会静默卡在 running。
- **不实现 reaper / 定时收割**。代价：若 executor 进程在 `mark_failed` 之前被 OOM/回收，任务会停在 running。由于评测任务可由调用方重新提交，且系统尚未大规模使用，接受此风险。

## 六、接口契约

### 6.1 认证

```
Authorization: Bearer {api_key}
```

- `api_key` 即 Web 控制台签发的完整 Key（`eval-…`），**仅创建时明文展示一次**。
- 平台按 token 哈希查 `api_keys`，校验存在 / 未吊销 / 未过期；通过即解析出 `{ projectId, orgId, apiKeyId }` 注入 `req.tenant`。
- 项目归属完全由 Key 决定：提交时**不接受也不应传入** `project_id`。
- **一把 Key 走天下**：同一把 Key 既提交任务、又查状态、又取速览（沿用 D3），不再细分 scope。

### 6.2 提交评估任务

```bash
POST /api/v1/jobs
Authorization: Bearer <api_key>
```

#### 6.2.1 上传原始字节（application/octet-stream）

适合提交 HTML / Markdown / 压缩包等已有文件。

```bash
curl -X POST https://eval.bj33smarter.com/api/v1/jobs \
  -H "Authorization: Bearer $API_KEY" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @unit-fractions.zip \
  -G \
  -d "filename=unit-fractions.zip" \
  -d "rule_set_id=coursework-quality" \
  -d "task_title=三年级数学-分数入门(单元)"
```

查询串字段：

| 字段 | 必需 | 类型 | 说明 |
|------|------|------|------|
| `filename` | 是 | string | 文件名，如 `lesson.html`、`unit.zip` |
| `rule_set_id` | 否 | string | 规则集，默认 `coursework-quality` |
| `task_id` | 否 | string | 自定义任务标识 |
| `task_title` | 否 | string | 任务标题 |
| `task_subject` | 否 | string | 任务学科 |

#### 6.2.2 内联 JSON（application/json）

适合直接传文本，无需落盘。

```json
{
  "content": { "filename": "lesson-01.md", "text": "# 分数入门 第1节 ..." },
  "rule_set_id": "coursework-quality",
  "task_id": "math-2024-q1",
  "task_title": "分数入门-第1页"
}
```

#### 6.2.3 响应（202 Accepted）

```json
{
  "job_id": "d3f1...e8a2",
  "status": "queued",
  "project_id": "9b30ef3c-867b-4110-8799-b49c1d4db32b",
  "poll_url": "/api/v1/jobs/d3f1...e8a2",
  "scf_request_id": "6a2b..."
}
```

> `scf_request_id` 仅在生产 `TENCENT_SCF_ENABLED=true` 时返回；本地 worker 模式为 null。

### 6.3 查询任务状态

```bash
GET /api/v1/jobs/{id}
Authorization: Bearer <api_key>
```

响应字段：

| 字段 | 说明 |
|------|------|
| `job_id` / `status` | 任务 id 与当前状态 |
| `project_id` / `org_id` | 归属（来自 API Key） |
| `input_kind` / `scope` | `upload` / `inline`、`unit` / `single` |
| `rule_set_id` / `task_id` / `task_title` | 提交时传入 |
| `run_id` | 评估运行 id（进入 running 后填充） |
| `web_run_url` | Web 平台运行详情页（完成后可访问） |
| `metrics` | 指标（completed 后），含 `_executor` 透明度字段 |
| `error` | **任务执行**失败原因（failed 后，`{message, traceback}`）——仅 executor 崩溃/异常；注意这是"任务崩了"，**不是**"评测没过" |
| `created_at` / `started_at` / `finished_at` | 各阶段时间戳 |

> 想知道"评测过没过 / 各项为什么没过"，看 §6.6 速览接口，不在此字段。
>
> 越权访问（`job_id` 不属于当前 Key 的项目）一律返回 `404`，不泄露存在性。

### 6.4 规则集目录

```bash
GET /api/v1/rule-sets
Authorization: Bearer <api_key>
```

返回构建期生成的静态 catalog，含各规则集所需能力（`["llm"]` / `["llm", "vision"]` 等）。

### 6.5 错误码

| HTTP | code | 含义 |
|------|------|------|
| 202 | — | 提交成功，任务已入队 |
| 400 | `INPUT_INVALID` | 字段缺失或非法（如缺 `filename` / `content`） |
| 401 | `AUTH_INVALID` | 缺少/错误的 API Key、Key 已吊销或过期 |
| 404 | `JOB_NOT_FOUND` | 任务/运行/样本不存在或不属于当前 Key 的项目（不泄露存在性） |
| 409 | `CANCEL_FAILED` | 非 `queued` 态调用取消（如实现取消） |
| 413 | `PAYLOAD_TOO_LARGE` | 上传内容超限（默认 50MB） |
| 429 | `RATE_LIMITED` | 触发令牌桶限流（按 API Key），带 `Retry-After`（限流见 §十） |

### 6.6 评测速览接口

第三方后端用 API Key 调用**单个**速览端点，一次拿到"过没过 / 多少分 + 各评测项失败原因"。数据复用 Query 仓储，按 Key 的 `projectId` 隔离，越权返回 `404`。

```bash
GET /api/v1/jobs/{id}/overview
Authorization: Bearer <api_key>
```

```jsonc
{
  "job_id": "0bc0b717-...",
  "run_id": "ded2dcc7-4fe2-418c-8567-85cf4f0240a1",
  "status": "completed",
  "web_run_url": "https://eval.bj33smarter.com/run/ded2dcc7-...",   // 嵌入此 URL 看完整详情（项目须公开，见 §3.5）
  "verdict": "fail",                                                 // pass | fail：综合是否达标(按 thresholds)
  "score": 0.781,                                                    // 综合分 = avg_reward
  "metrics": { "DR": 0.962, "CPR": 0.914, "condR": 0.842 },
  "summary": { "total": 24, "passed": 18, "failed": 5, "skipped": 1 },
  "dimension_pass": { "format": 23, "commonsense": 21, "soft": 19, "preference": 22 }, // 各维度通过样本数(速览哪类问题多)
  "items": [                                                         // 各评测项(样本)
    {
      "external_sample_id": "三年级数学-分数入门-第1页",
      "score": 0.42, "passed": false,
      "failures": [                                                  // 该项失败原因(未通过约束)
        { "name": "常识性检查", "reason": "1/2 与 1/3 图示面积颠倒，未引入分子/分母术语" }
      ]
    }
  ]
}
```

说明：

- `items[].failures[]` 聚合自该样本未通过约束的 `name`+`reason`（来源同前端样本页，见 [09](./09Web可观测平台架构设计.md) §十）；速览**只给摘要**，不给 `details`/`module_results`/制品——这些走 iframe 嵌入公开页查看。
- `verdict` 由平台按 `thresholds` 综合判定（DR/CPR/reward 达标且无 `hard_gate` 失败 = `pass`）。
- 任务未完成（`queued`/`running`/`failed`）时，速览返回 `status` + 任务级 `error`，`items` 为空。

## 七、课件平台呈现

### 7.1 任务状态流转呈现

课件平台侧的状态映射（直接消费查询结果）：

| `job.status` | 课件平台展示 | 交互 |
|---------------------|--------------|------|
| `queued` | "排队中" | 可取消（如实现） |
| `running` | "评测中" | 可查看 Web 实时页 |
| `completed` | "评测完成" + 总分 | 可看结果详情 |
| `failed` | "评测失败" + 原因 | 可重新提交 |

### 7.2 结果呈现（速览 + 嵌入）

两者配合：**速览**给课件平台自渲染"过没过 + 各项原因"的列表；**嵌入**给用户点进某条看完整详情。

**A. 速览（自渲染摘要）**——一次调用拿到全部：

```ts
const ov = await get(`/api/v1/jobs/${jobId}/overview`);          // verdict + score + items
render(`${ov.verdict === "pass" ? "通过" : "未通过"} · ${ov.score} 分`);
ov.items.filter(i => !i.passed).forEach(i =>
  render(i.external_sample_id, i.score, i.failures.map(f => `${f.name}：${f.reason}`))
);
```

**B. 嵌入（看完整详情）**——项目公开后，直接放 URL，无需后端换签：

```tsx
// web_run_url 来自 /jobs/{id} 或 /jobs/{id}/overview；项目须已设为公开
<iframe src={ov.web_run_url} className="w-full h-[800px]" />
```

> 典型组合：列表用 A（速览自渲染"哪些项没过、为什么"），点某项用 B（iframe 看 该样本的逐条约束 / 制品预览）。

## 八、部署方案

### 8.1 Docker 化（开发 / 通用部署）

本地 `docker-compose.yml` 已包含 `web` 与 `executor` 两个服务：

```yaml
services:
  web:
    build: ./docker/web
    env_file: ./.env
    ports: ["9000:9000"]
    depends_on: [postgres, minio]
  executor:
    build: ./docker/executor
    env_file: ./.env
    environment:
      EVALEXECUTOR_WORKER_ENABLED: "true"
      AGENT_EVAL_HOST: http://web:9000
      AGENT_EVAL_UPLOAD: "true"
    depends_on: [postgres, minio, web]
```

- `TENCENT_SCF_ENABLED=false`：Web 写入 `public.eval_jobs` 后，由 `executor` worker 模式轮询执行。
- 第三方对接地址指向 Web 后端 `http://localhost:9000`。

### 8.2 腾讯云函数（SCF）适配（生产）

| SCF 函数 | 触发器 | 职责 | 超时 |
|----------|--------|------|------|
| `agent-eval-web` | API 网关（HTTP，同步） | 接收任务、查状态、提供 Ingestion/Query API | 短（如 30s） |
| `agent-eval-executor` | SCF Invoke Event（异步） | 消费任务 → 下载输入 → `eval_packages()` → 回传 | 86400（需开启异步执行） |

适配要点：

1. **状态外置**：`public.eval_jobs` 与 Web 共享同一云 PG（CDB），经 PgBouncer 连接池应对 SCF 短连接。
2. **对象存储与大文件**：输入/制品均经 presigned URL 流转，executor 不持对象存储凭据。
3. **端口约定**：Web 函数监听 `9000`（对齐 SCF 默认）。
4. **冷启动**：executor 依赖评估器与 LLM 客户端，镜像需预热/精简；评估器已离线优先，冷启动影响可控。
5. **健康检查**：`GET /api/v1/health` 与 `GET /health` 供探活。

### 8.3 配置管理

相关环境变量纳入 `.env.example`：

| 变量 | 说明 |
|------|------|
| `TENCENT_SCF_ENABLED` | 本地 false，生产 true |
| `TENCENT_SCF_REGION/NAMESPACE/FUNCTION_NAME` | SCF executor 配置 |
| `TENCENT_SECRET_ID/SECRET_KEY` | SCF Invoke 签名凭据 |
| `PLATFORM_KEY_ENCRYPTION_KEY` | 解密提交者 token（Web 与 executor 必须一致） |
| `AGENT_EVAL_HOST` / `AGENT_EVAL_UPLOAD=true` | executor 回传 Web 地址与开关 |

安全红线遵守项目约定：密钥严禁入库，走 `.env` / SCF 环境变量。

## 九、Web 接入文档页（面向第三方）

前端接入文档位于 `web/frontend/src/content/integration.md`，由前端页面静态渲染。内容应随接口变更同步更新，包含：

1. **概述**：对接流程一张图（提交 → 状态 → 速览 → 嵌入）。
2. **准备**：在平台创建 Project → 签发 API Key →（可选）把项目设为**公开**以便嵌入。
3. **鉴权**：`Authorization: Bearer {api_key}`（一把 Key 走天下）。
4. **提交任务**：`POST /api/v1/jobs` 示例（octet-stream / JSON inline、单元/单页）。
5. **看结果**：轮询 `GET /jobs/{id}`（状态）→ `GET /jobs/{id}/overview`（速览：过没过 + 各项失败原因）。
6. **iframe 嵌入**：项目公开后，直接 `<iframe src={web_run_url}>`，无需令牌。
7. **MCP 接入（智能体）**：远程 MCP server 配置（`url + headers:Authorization`）+ 工具清单（提交/查询/速览/规则集/大文件上传），见 §3.7。
8. **状态码 / 错误码**：表。
9. **课件平台集成示例**：状态流转 + 速览自渲染 + 嵌入详情的最小代码（见 §7.2）。
10. **限额与约束**：上传上限、并发、保留期。

## 十、安全

| 项 | 措施 |
|----|------|
| 鉴权 | 统一 Bearer API Key（提交 / 查状态 / 取速览）；一把 Key 绑定单一项目 |
| 多租户隔离 | 所有读写按验签所得 `project_id/org_id` 过滤；越权返回 404；速览接口复用 Query 仓储的强制过滤 |
| 公开项目 | owner 显式开启 `Project.isPublic` 后，该项目运行/样本详情**免登录可读**（任何人持链接可看）；仅**只读**，不暴露任何写操作或 Key；URL 含不可猜测 UUID 但非秘密——开启前须告知 owner |
| iframe 防护 | 公开项目的运行/样本页放开 `frame-ancestors`（允许第三方嵌入）；其余页面保持 `X-Frame-Options: SAMEORIGIN`；嵌入页只读、无敏感入口，clickjacking 风险受限 |
| 凭据 | executor 不持对象存储凭据；服务级凭据走 `.env` / SCF 环境变量；严禁入库 |
| 上传安全 | zip 解包限制解压总大小与文件数、路径穿越（zip-slip）防护 |
| 限流 | 复用令牌桶（按 API Key） |
| 审计 | 调试台提交、Key 签发/吊销、项目公开开关变更写入 `AuditLog` |
| LLM 凭据 | 评估所需 LLM Key 由 executor 侧持有，不暴露给第三方 |

## 十一、风险与权衡

| 风险 | 影响 | 缓解 |
|------|------|------|
| 评估长耗时 vs SCF 超时 | 任务超时失败 | executor 部署为 SCF 事件函数 + 异步执行（24h） |
| SCF 异步执行无平台重试 | 进程崩溃则任务卡死 | 启动即 `mark_running` + try/except `mark_failed`；不做 reaper，接受极小概率残留 |
| SCF 冷启动慢（镜像函数） | 首任务延迟高 | 生产配预置并发；presigned URL 时效覆盖冷启动 |
| presigned URL 过期 | executor 下载失败 | TTL 1h；必要时 executor 回调 Web 重新签发 |
| 第三方内容体积/安全 | 解压炸弹 | 上传限额 + 解压大小/数量上限 + zip-slip 防护 |
| 本地开发与 SCF 行为差异 | 线上才暴露问题 | 本地用 worker 模式 + MinIO，保持代码路径一致 |
