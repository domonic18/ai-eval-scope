> 本计划基于 [02 配置管理开发计划](./02配置管理开发计划.md) v1.2.0 的**端到端诊断**制定。
>

## 〇、背景：诊断结论（证据链）

逐环节真实状态（均带代码证据，源自 2026-07-23 端到端诊断）：

| 环节 | 状态 | 关键证据 |
|---|---|---|
| ① Web 编辑场景包 | 🟡 基本可用 | 资产草稿隔离 OK；但场景级 defaults 未版本化，编辑即上线（`scenarios.ts:74-103`） |
| ② 发布版本+标签 | 🟡 能跑但有硬伤 | 同版本可覆盖（`scenario.repository.ts:83-100` 等）；标签非互斥（`:254-271`）；两套"最新"解析不一致（`:296-328` vs `ruleSets.ts:32-37`） |
| ③ executor 取最新版 | 🔴 **四层全断** | 见下 |
| ④ 运行快照 | 🔴 空壳 | version 硬编码 1.0.0（`snapshot.py:61`）；指标取本地默认（`:44,64`）；两调用方不传 rule_set（`sink.py:115-122`、`cli/main.py:431-435`） |
| ⑤ 动态展示 | 🟡 仅 courseware | 前端硬编码 `scenarioId="courseware"`（`RunDetail.tsx:83`） |

### ③ 为什么完全不通（四层全断）

1. **evaluator 客户端**：`get_remote_client()` 恒返回 `None`（`packages/remote_client.py:51-57`）；`agent-eval package pull` 永远 `exit 1`（`cli/package.py:130-156`）。
2. **Web 读端点**：无 `pull-token` 端点、无返回包内容的 GET 端点；`scenario_packages` 表**只写不读**；不走对象存储。
3. **executor**：从不调用 pull；用镜像构建期烧死的内置 YAML（`runner.py:37-46`、`rules/registry.py:32-57`）；**未知 id 静默回退 `coursework-quality.yaml`**（正确性隐患）。
4. **job 契约**：`eval_jobs.rule_set_id` 仅字符串、无版本（`models/db.py:37-39`）；SCF payload 同（`infra/scf.ts:15-25`）；路由 `package_id` 只是 `rule_set_id` 别名（`routes/eval/jobs.ts:42,50`）。

**结论**：今天"更新场景包" = 重新发版 evaluator pip 包 + 重建 executor 镜像，**不是**「Web 发布即生效」。02 计划里程碑"本地 CLI 可从 Web pull 包"（行 162）**未达成**。

## 一、架构决策（ADR-01）

### 决策

**采用「运行时拉取（Runtime Fetch）」+ 复用现有 API Key 鉴权，砍掉 `pull-token` 机制。**

> executor 在执行 job 时，以现有 API Key（回传结果所用同一凭证）向 Web 请求 `GET /api/v1/scenarios/:id/packages/:assetId?label=production`，拿到解析好的包内容，写入本地缓存后加载执行。

### 理由（面向开源 · 行业最佳实践 · 不过度设计）

1. **executor 是可信常驻客户端**：它已持 API Key 与 Web 通信（回传 run 结果即用此鉴权）。再叠一套 `pull-token` 短期 JWT（原设计 §11.2）是冗余的第二套鉴权——`pull-token` 是「包注册中心模型」（npm/PyPI/HF Hub，面向不可信/临时消费者），与本系统的可信客户端关系不匹配。
2. **符合同类开源系统实践**：Langfuse SDK / Helicone 等「托管配置 + 运行时执行」型系统，均由可信客户端用 API Key 运行时 GET 自身配置。
3. **不过度设计**：去掉 pull-token 整条机制（含 token 签发/校验/传递），减少一个鉴权域与相应测试面。

### 不选其它方案的理由

- **不选 B（job 下发包内容）**：耦合「派发」与「包内部」；腾讯 SCF `ClientContext` payload ~6MB 上限，稍大包放不下，最终仍需对象存储 + URL，等于本方案绕一圈。
- **不选 C（只修 bug，保留构建期更新）**：不满足「executor 获取最新版本」的运行时诉求。

### 明确「不做」的边界（YAGNI）

| 不做 | 何时再做 |
|---|---|
| 对象存储归档（MinIO/COS） | 包体 > ~1MB 阈值时再引入；当前 courseware 包为 KB 级，JSONB 内联即可 |
| `pull-token` 短期 JWT 机制 | 不做（本 ADR 砍除） |
| Phase 6 插件框架（ScenarioPlugin/entry-points） | 闭环稳定后另议 |
| 联网自动 pull fallback（resolve 未命中自动拉） | 先显式按需拉；自动 fallback 作为后续增强 |
| Phase 7 benchmark / Phase 8 新场景 | 不在本计划范围 |

## 二、开发原则

- **做实而非做新**：本计划只加固已有能力、打通断点，不新增评估场景/能力。
- **无向后兼容包袱**：job 契约变更（增 `package_ref`）需一次性迁移；旧 `rule_set_id` 字符串语义升级为包引用。
- **测试先行 · 禁联网**：HTTP/对象存储/SCF 调用全部 mock；文件系统用 `tmp_path`。
- **文档同步**：完成即回写 02 计划状态、arch/13 相关章节、本 ADR。

## 四、验收标准

### 4.1 端到端验收（Slice 2 完成后必须通过）

1. 在 Web 编辑并发布 courseware 包的一个**新版本**（如改某指标阈值），打 `production` 标签。
2. executor 触发一次 job（payload 带新 `package_ref`）。
3. 断言：executor 加载的是**新版本**规则集（日志/快照 version 一致）；快照 `metric_definitions` 反映新阈值；可观测页展示新指标。
4. 回归：courseware 既有评估结果与改前一致（除被改指标外）。

### 4.2 各 Slice 通用标准

- Web：`cd web/backend && npm run lint && npm run typecheck && npm test` 通过。
- evaluator：`uv run ruff check && uv run pytest` 通过；HTTP 全 mock。
- executor：相关单测通过；`format-only` 冒烟仍绿。
- 每个新增端点/客户端有集成测试（mock 远端/SCF）。

### 4.3 「不过度设计」核对表（交付前自查）

- [ ] 未引入 pull-token 任何代码
- [ ] 未引入对象存储（除非确有包 > 阈值，且单独说明）
- [ ] 未引入 Phase 6 插件抽象
- [ ] 未引入联网自动 pull fallback
- [ ] 鉴权复用现有 API Key，无第二套凭证

## 五、依赖与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| job 契约变更（`rule_set_id` → `package_ref`）影响在途 job | 中 | 一次性迁移 + 兼容窗口；旧 job 显式拒绝并提示重提 |
| executor 运行时拉取增加 SCF 冷启动延迟/出口流量 | 中 | 本地缓存按 version/contentHash 去重，仅变更时重拉；包体小（KB 级） |
| 版本不可变改造影响已有「重发同版本」的运维习惯 | 低 | S1-2 迁移期保留诊断信息，引导升版本 |
| 删除 `_BUILTIN` 可能遗漏某些隐式依赖 | 低 | 全仓 grep `rule_set_id`/`get_path` 调用点；冒烟 + 集成测试兜底 |
| 快照结构变化（S2-11~14）与历史快照不兼容 | 低 | 历史快照保留；新字段缺失时优雅降级（已有 `defaultDefs` 回退路径） |
