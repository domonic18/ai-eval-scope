## 二、v1.2.0 计划外重大变更（实现期沉淀）

实现 Phase 0-5 过程中，相对 v1.1.0 原计划产生两项重大变更，已沉淀为设计文档并落地：

### 2.1 规则层 `method` 声明式评估方式与条件化资产绑定
- **背景**：原 schema 仅 `evaluator` 字符串（如 `format.response_format`、`commonsense.info_accuracy`），UI 无法据其渲染交互、资产绑定藏在 `params`/Python 类属性里，新增评估方式需同时改 YAML/Python/前端，耦合严重。
- **变更**：`Rule`/`RuleTemplate` 新增 `method`（llm/llm_vision/rule_set/format）+ `prompt_id` + `confirmation_prompt_id` + `dataset_ids` + `format_type` + `extensions`，`evaluator` 降为可选（缺失时由 method+资产派生）。**无向后兼容**——旧 `evaluator`-only 规则不再支持，内置规则集已全量迁移。
- **复合评估器建模**：`commonsense.info_accuracy` 为复合评估器（KB 事实校验 → LLM 验证 → LLM 裁定），用 `prompt_id`（info_accuracy）+ `confirmation_prompt_id`（fact_verdict）双提示词建模，引擎映射到 `params.prompt_id`/`params.fact_verdict_prompt_id`，评估器零改动。
- **文档**：[14 配置编辑器交互设计](../arch/13配置管理设计.md) §一/§二/§三 涵盖根因与方案。
- **关联任务**：P0-1（模型扩展）实际范围大于原计划，含 method/绑定字段。

### 2.2 统一场景包编辑器（双编辑器收敛）
- **背景**：原 P4 设想 ConfigHub + 各资产独立编辑器，实现期出现 AssetEditor（独立页）与 PackageEditor（树形包编辑器）两个并行编辑器，入口分散、草稿语义矛盾、跨资产跳转依赖 localStorage/sessionStorage 补丁，连续暴露多个缺陷（草稿覆盖已发布内容、跳转白屏崩溃、回链自显等）。
- **变更**：收敛为**唯一编辑器** `/edit?select=<kind>:<assetId>`（URL 即状态）；AssetEditor 退役为 301 重定向；统一草稿语义（显式恢复，绝不静默覆盖）；引用跳转改为树内定位 + Tab 多开；新建资产本地草稿化（不发骨架版本）；发布引用完整性校验 + 批量发布。
- **文档**：[14 配置编辑器交互设计](../arch/13配置管理设计.md) 完整方案与 P1 收敛 / P2 增强 / P3 打磨分阶段。
- **关联任务**：P4-1~6 实际实现形态为统一编辑器，超出原计划。

## 二、总体策略

### 2.1 开发原则

- **自底向上**：先落地 evaluator 侧的包管理、DatasetBackend、ScenarioPlugin 等基础设施，再补齐 Web 编辑器与线上仓库。
- **MVP 优先**：Phase 0-3 优先完成课件场景自身的配置化与 Web 可视化；Phase 4 之后逐步扩展新场景与 benchmark 数据集。
- **无向后兼容 / 无 fallback**：对齐 [09 §9.5.6](../arch/09Web可观测平台架构设计.md)，历史数据通过**一次性迁移脚本**补齐 `metrics` JSONB 与 `RunConfigSnapshot`，前端**不保留**任何课件专用兜底；迁移并验证完成后 DDL 删除遗留列与硬编码常量。
- **测试先行**：每个新增模块必须附带单元测试；涉及 HuggingFace / 对象存储 / API 的测试必须 mock，禁止联网。
- **文档同步**：每完成一个 Phase，同步更新 [13 配置管理设计](../arch/13配置管理设计.md) 与对应联动架构文档的实现状态。

## 七、验收标准

### 7.1 Phase 交付标准

每个 Phase 结束必须满足：

1. 新增代码通过 `make check` 与 `cd web/backend && npm run lint && npm run typecheck`。
2. 新增功能附带单元测试，覆盖率不低于 80%。
3. 涉及网络/IO 的测试使用 mock，禁止联网。
4. 相关架构文档章节（见 §四）更新为「已实现」。
5. 提交遵循 Conventional Commits，MR 至少 1 人 review。

### 7.2 最终交付标准

- 本地可创建、验证、拉取、运行 Scenario Package。
- Web 可编辑 RuleSet、PromptTemplate、Dataset，支持版本与标签。
- 每次 Run 保存完整配置快照并可追溯。
- **Web 可观测页指标完全场景化**：`lib/eval.tsx` 课件硬编码常量删除，`Run`/`Sample` 遗留指标列删除，历史数据经一次性迁移补齐，无任何 fallback。
- 支持 courseware、GSM8K、travel-itinerary、conversation-safety、code-generation、RAG 至少 6 个场景/包。
- 新场景可通过 `ScenarioPlugin` 与 entry-points 扩展，无需修改核心代码。
